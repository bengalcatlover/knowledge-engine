# 使える武器

## 1. 要求定義と受入基準の設計

**武器：Requirements Definition、要求の階層化、検証可能な受入条件**

顧客の「AIで業務を効率化したい」という曖昧な要望を、次のような検証可能な要求に変換する。

- 問い合わせの80%は自動分類できる
- 回答生成のレイテンシは3秒以内
- 高リスク領域では必ず人間承認を要求する
- CRMに記録されない回答は本番リリースしない
- 誤回答率だけでなく、エスカレーション率と顧客満足度も測定する

AIプロダクトでは、モデル性能だけでなく、データ入力、権限、UI、人間の介入、ログ、障害時の代替フローまで要求として定義できる。

**適用先**

- AI導入案件の要件定義
- SaaSプロダクトのPRD作成
- 業務自動化のRFP・受入テスト設計
- コンサルティングにおける「課題の再定義」

## 2. Vモデルによる検証・妥当性確認

**武器：Vモデル、VerificationとValidationの分離**

- **Verification**：設計したものを正しく作ったか
- **Validation**：そもそも顧客・利用現場にとって正しいものを作ったか

例えば、AI請求書処理では次のように分解する。

| 段階 | 確認内容 |
|---|---|
| 要求 | 95%以上の請求書を自動処理する |
| 設計 | OCR、項目抽出、ERP連携、例外処理の構成 |
| Verification | 各API、抽出器、バリデーションのテスト |
| Validation | 経理担当者が月末処理を本当に短縮できるか |
| 運用 | 誤処理率、手戻り、監査対応を継続監視 |

AIでは、精度テストだけでなく、エッジケース、データ分布の変化、拒否・エスカレーションの挙動も検証対象にできる。

## 3. システムアーキテクチャとインターフェース管理

**武器：アーキテクチャ分解、インターフェース管理、統合設計**

AIエージェントを導入する場合、単にモデルを選ぶのではなく、以下のシステムとして設計する。

1. ユーザーインターフェース
2. 認証・権限管理
3. 検索・データ取得
4. 基盤モデル
5. 業務ルール
6. 人間による承認
7. ERP・CRMへの書き込み
8. ログ・監査・監視

各コンポーネントの間で、データ形式、責任範囲、エラー処理、タイムアウト、再実行条件を定義する。AI案件で頻発する「モデルは動くが業務システムに組み込めない」という問題を、インターフェース問題として扱える。

## 4. トレードスペース探索

**武器：複数の設計案を可視化し、Pareto最適な選択肢を比較する**

例えば生成AI基盤を選ぶ際に、以下を同時評価する。

- 精度
- レイテンシ
- 1リクエスト当たりのコスト
- データ越境リスク
- 監査可能性
- カスタマイズ性
- 運用負荷

「最高精度のモデル」を選ぶのではなく、精度とコスト、速度、リスクの組み合わせを複数案として比較できる。

**具体的な意思決定例**

- 高精度だが高価なモデルを重要案件だけに使う
- 低リスクのFAQは小型モデル、例外処理だけ大規模モデルに送る
- 完全自動化ではなく、人間承認を含む半自動化を選択する

## 5. Value Stream Mappingによる業務可視化

**武器：業務の流れ、待ち時間、手戻り、引き継ぎ、価値付加時間の可視化**

例として、カスタマーサポートの問い合わせ処理を可視化する。

- 顧客からの受付
- 担当部署への転送
- 顧客情報の検索
- 回答案の作成
- 上長承認
- 顧客への返信
- CRMへの記録

実作業が10分でも、部署間の待ち時間や承認待ちで全体リードタイムが2日になることがある。AI導入前にVSMを作れば、「どこにAIを入れるべきか」を誤らずに済む。

**測定できる指標**

- エンドツーエンドのリードタイム
- 実作業時間と待ち時間
- 引き継ぎ回数
- 手戻り率
- 一次回答率
- 顧客の再問い合わせ率

## 6. 変動性とSix Sigma型の改善

**武器：平均値ではなく、ばらつきと異常値を扱う**

業務改善では平均処理時間だけを見ると不十分である。例えば、通常時は5分で処理できても、月末には30分になるなら、顧客体験や人員計画に大きな問題が残る。

適用例：

- コールセンターの待ち時間の時間帯別変動
- AI推論レイテンシのピーク時変動
- 需要予測誤差の顧客・商品別分布
- 倉庫ピッキング時間の作業者別ばらつき
- 医療現場の受付から診療までの時間分布

改善前後で平均、分散、上位パーセンタイル、不良率を比較し、単なる「印象の改善」と区別する。

## 7. A3 Thinkingによる問題解決

**武器：問題を一枚の構造化されたストーリーにする**

A3の考え方を使うと、改善会議を「誰が悪いか」の議論から、以下の議論に変えられる。

1. 現状は何か
2. 目標との差はどれだけか
3. 何が根本原因か
4. どの対策を試すか
5. 効果をどう測るか
6. 標準化・横展開をどう行うか

例として、AI導入後も処理時間が減らない場合、原因を「AIの精度不足」と決めつけず、データ入力、承認、例外処理、システム間コピー、教育不足に分解する。

## 8. 航空運航から学ぶリスクベースの意思決定

**武器：運用条件、最低基準、代替策、Go/No-Go判断**

ドローン配送や自動運転、現場ロボットでは、単に「技術的に動くか」ではなく、以下を事前に判断する。

- 天候や通信環境は許容範囲か
- 機体・システムの残余能力は十分か
- 代替ルートや緊急停止手順はあるか
- 失敗時に人や資産へどの程度影響するか
- どの条件で運用を中止するか

例えば、配送AIが高い予測精度を持っていても、通信断、GPS異常、悪天候、バッテリー低下時のフェイルセーフがなければ本番投入できない。

## 9. ライフサイクル管理とコミッショニング

**武器：導入・運用・保守・変更・廃止を一つの設計対象として扱う**

業務自動化の導入時には、以下をあらかじめ設計する。

- 本番前の受入試験
- シャドーモード運用
- 段階的なロールアウト
- モデル・ルール変更時の再検証
- 監視指標とアラート
- 障害時の手動運用
- 運用終了時のデータ移行・削除

AIプロダクトでは、リリース日よりも、リリース後にデータ分布や業務ルールが変わったときに品質を維持できるかが重要になる。

## 10. 迅速なプロトタイピング

**武器：大規模開発の前に、リスクの高い仮説を小さく検証する**

プロトタイプを「完成品の縮小版」ではなく、「最も不確実な仮説を検証する道具」として使う。

例：

- AIエージェントの実装前に、手作業＋簡易UIで業務価値を検証
- 自動運転・ドローンなら、限定環境で認識・経路・停止条件を試験
- ハードウェアなら、重量、電力、熱、接続、操作性のどれがボトルネックかを先に確認
- 新しい業務フローなら、1チーム・1顧客・1種類の帳票でパイロットを行う

## 11. Active LearningとHuman Factorsを使った導入

**武器：講義型の一方向教育ではなく、実践・質問・フィードバック中心の導入**

新しいAIツールや自動化を社内に展開する際に、単なるマニュアル配布ではなく、

- 実際の案件を使った演習
- 判断が分かれるケースへの質問
- 失敗例の共有
- 操作後のフィードバック
- 講師ではなくコーチとしての支援

を組み込む。

特に高リスク業務では、「AIの答えを信じる」ことを教えるのではなく、いつ疑い、いつ人間にエスカレーションするかを訓練する必要がある。

# キーコンセプト

1. **要求定義（Requirements Definition）** — 顧客・利用者の期待を、設計・試験で確認できる具体的な要求へ変換する。**MIT 16.842 Fundamentals of Systems Engineering**。
2. **Vモデル** — 左側で要求・設計を分解し、右側で各階層を統合・検証する開発フレームワーク。**MIT 16.842**。
3. **VerificationとValidation** — 「仕様どおり作ったか」と「本当に必要なものを作ったか」を分けて確認する。**MIT 16.842**。
4. **MBSE／システムモデリング** — 文書だけでなく、システム要素・関係・要求・状態をモデルとして管理する考え方。**MIT 16.842**。
5. **システムアーキテクチャ** — 機能を構成要素に割り当て、全体の構造と責任分担を決める設計。**MIT 16.842、MIT 16.885J**。
6. **インターフェース管理** — 部品・チーム・システム間のデータ、物理接続、責任、エラー処理を明確化する。**MIT 16.842**。
7. **トレードスペース探索** — コスト、性能、重量、リスク、納期など複数の評価軸で設計案を比較する方法。**MIT 16.842**。
8. **学際的最適化（Multidisciplinary Optimization）** — 機械、電気、ソフトウェア、運用など相互依存する設計変数を同時に最適化する。**MIT 16.842**。
9. **システム統合** — 個別には動く要素を、実際の運用環境で一つのシステムとして動作させる工程。**MIT 16.842、MIT 16.885J**。
10. **ライフサイクル管理** — 要件、設計、製造、コミッショニング、運用、保守、廃止までを連続した対象として管理する。**MIT 16.842**。
11. **Lean思考** — 顧客価値を基準に、価値を生まない活動や待ち、手戻りを減らして流れを改善する。**MIT 16.660、MIT 16.660J**。
12. **Value Stream Mapping** — 業務の流れを、処理時間・待ち時間・在庫・手渡し・情報の流れとして可視化する。**MIT 16.660J / ESD.62J / 16.853**。
13. **A3 Thinking** — 問題、現状、根本原因、対策、効果確認を一枚の構造化されたストーリーにまとめる。**MIT 16.660J / ESD.62J / 16.853**。
14. **変動性（Variability）** — 平均値だけでなく、処理時間・需要・品質のばらつきがシステム性能を左右するという考え方。**MIT 16.660J / ESD.62J / 16.853**。
15. **Six Sigma型の品質改善** — 測定データに基づき、原因を分解し、不良・誤差・ばらつきを低減する改善方法。**MIT 16.660、MIT 16.660J**。
16. **重量・重心・性能制約** — ある設計の性能は、単一の機能ではなく、重量配分、容量、燃料・電力などの制約の組み合わせで決まる。**MIT 16.687 Private Pilot Ground School**。
17. **運用限界とGo/No-Go判断** — 気象、空域、機体状態、代替策などを踏まえ、実施・延期・中止を判断する。**MIT 16.687**。
18. **ヒューマンファクター** — 人の認知限界、コミュニケーション、注意、疲労、判断ミスを前提にシステムを設計する。**MIT 16.687**。
19. **迅速なプロトタイピング** — 完成品を作る前に、最もリスクの高い技術・顧客・運用仮説を小さく検証する。**MIT 16.810 Engineering Design and Rapid Prototyping**。
20. **Active Learning／コーチ型教育** — 一方的な知識伝達ではなく、質問、演習、フィードバック、振り返りによって実践能力を高める。**MIT 16.06 Principles of Automatic Control, How We Teach**。

# 薄い/ない領域

## 1. 航空宇宙工学の基礎理論

Private Pilot Ground Schoolでは概念的な航空力学、性能、気象などを扱うが、以下のような数学・物理ベースの専門内容は薄い。

- 流体力学と定量的な空力解析
- 飛行力学、安定性、操縦性
- 航空機構造、疲労、複合材
- 推進工学、タービン、ロケットエンジン
- 熱力学、伝熱、燃焼
- 詳細な航空機設計計算

## 2. 宇宙工学・Astronautics

この講義群では、宇宙分野はほぼカバーされていない。

- 軌道力学、天体力学
- ロケット推進、打上げ軌道
- 宇宙機の姿勢・軌道制御
- 宇宙機の電源、熱、通信、姿勢決定
- ミッション設計とコンステレーション
- 宇宙環境、放射線、微小重力
- 再使用型宇宙輸送、ランデブー、ドッキング

## 3. 制御工学・自律システム

「How We Teach」は制御工学の講義を教える方法が中心であり、制御理論自体はほとんど確認できない。

- フィードバック制御
- 状態空間表現
- 安定性解析
- PID、最適制御、ロバスト制御
- カルマンフィルタ、状態推定
- SLAM、経路計画、ロボティクス
- 自律システムの安全設計

F-22飛行制御の特別講義はあるが、体系的な制御理論コースの代替にはならない。

## 4. 航空機ソフトウェア・アビオニクス

航空機システムの概念は扱われるが、以下の実装・認証領域は薄い。

- リアルタイムOS
- 航空電子機器・通信バス
- センサー融合

- ソフトウェア変更管理
- 航空機サイバーセキュリティ

## 5. 安全性・信頼性工学

## 6. データサイエンス、AI、MLOps

業務改善やシステム設計をAIに適用するための考え方は得られるが、AIの実装技術はほぼ対象外である。

## 7. サプライチェーンと事業経済性

## 9. 実際の事業成果を伴うケーススタディ

Leanや設計の演習、ヘルスケア事例、工場訪問はあるが、次のような企業成果の検証は限定的である。

- 導入前後の利益率

- プロセス改善の長期定着率

# 他分野との接続

## 1. ソフトウェア工学・プロダクトマネジメント

**移転する概念**

- 要求定義
- Vモデル
- インターフェース管理
- 統合テスト
- ライフサイクル管理
- 変更管理

**接続例**

AIプロダクトを、モデル単体ではなく、UI、データ、権限、API、監査ログ、人間承認を含むシステムとして管理できる。ソフトウェアのCI/CDにも、要求とテストのトレーサビリティという形で適用できる。

## 2. AI・データサイエンス

**移転する概念**

- トレードオフ分析
- 変動性
- 検証・妥当性確認
- モデル監視
- 人間によるエスカレーション
- プロトタイピング

**接続例**

モデル精度だけでなく、コスト、レイテンシ、データ品質、説明可能性、業務成果を同時に評価する。AIの本番運用では、モデルの精度低下を「品質問題」ではなく「システムライフサイクル上の劣化」と捉えられる。

## 3. オペレーションズ・コンサルティング

**移転する概念**

- Value Stream Mapping
- A3 Thinking
- 変動性分析
- 根本原因分析
- 継続的改善
- 標準化

**接続例**

コンサルティング案件で、経営層の抽象的な「生産性向上」を、プロセス単位のリードタイム、待ち時間、手戻り、承認回数、例外率に分解できる。業務改善施策の効果も、導入前後の分布で評価できる。

## 4. 製造業・サプライチェーン

**移転する概念**

- ムダの削減
- 流れ
- 品質の作り込み
- 変動性の制御
- 現場参加
- 迅速な試作

**接続例**

工場の不良削減だけでなく、部品調達、検査、修理、返品処理、倉庫ピッキングにも適用できる。製品設計時に、製造・保守・廃棄まで含めてアーキテクチャを考える点は、Design for ManufacturingやDesign for Serviceに接続する。

## 5. 医療オペレーション

**移転する概念**

- 患者フローの可視化

- 変動性シミュレーション
- A3による改善
- ヒューマンファクター

**接続例**

救急外来や検査部門で、平均待ち時間だけでなく、時間帯別の混雑、患者の滞留、スタッフの引き継ぎ、再検査率を分析する。医療AIでは、Vモデルと人間承認フローを組み合わせることで、診断支援と自動診断を区別できる。

## 6. 安全工学・リスクマネジメント

**移転する概念**

- 運用限界
- Go/No-Go判断
- チェックリスト
- ヒューマンファクター
- フェイルセーフ
- 代替手順

**接続例**

自動運転、ドローン、金融取引AI、医療AIなど、失敗コストが大きいシステムでは、「通常時の性能」だけでなく、異常時にどのように停止・縮退・人間へ移管するかを設計する。

## 7. 組織開発・チェンジマネジメント

**移転する概念**

- People: The Heart of Lean
- Active Learning
- コーチ型支援

- Concept Questions

**接続例**

新しい業務システムやAIを導入する際に、ツールを配布して終わりにせず、現場の疑問、反対理由、失敗パターンを取り込む。研修を一度の説明会ではなく、実案件を使った反復学習として設計する。

## 8. 戦略・ファイナンス

**移転する概念**

- トレードスペース
- ライフサイクルコスト
- リスクと性能の比較
- 設計案のPareto評価
- 段階的投資

**接続例**

新規事業やAI投資で、最初から最大規模のシステムを作るのではなく、限定的なプロトタイプ、パイロット、段階展開を組み合わせる。性能、コスト、規制リスク、導入期間を同一の意思決定表で比較できる。

ただし、NPV、価格戦略、資本配分、事業ポートフォリオの理論は、この講義群だけでは補完が必要である。

- 検証・妥当性確認

**接続例**

IoT製品やロボットでは、センサー、通信、電源、機械構造、クラウド、ユーザー操作を別々に最適化すると統合時に破綻しやすい。航空機設計で使うシステム全体の見方を、物流ロボット、産業機器、ウェアラブル機器に移転できる。
