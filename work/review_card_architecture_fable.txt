# 知識ベース設計への提言

## 1. OOP参照モデルの妥当性評価

**有効な比喩（採用推奨）**

| OOP概念 | 知識カードへの適用 |
|---|---|
| クラス vs インスタンス | 概念カード（再利用可能な抽象）と実例（具体事例）の分離。混在が最大の劣化要因 |
| インターフェース | カードの必須スロット定義（定義・根拠・関係・出典）をスキーマとして固定 |
| 単一責任原則 | 1カード=1概念。「〜と〜の関係」を1枚に詰めない |
| 継承の浅さ推奨 | is-a階層は2〜3段まで。深い分類学は保守コストが跳ねる |
| コンポジション優先 | 概念の合成は関係リンクで表現し、巨大カードを作らない |

**危険な比喩（採用禁止）**

- **カプセル化**: 知識は隠蔽せず全リンクを可視化すべき。OOPと逆
- **網羅的クラス階層の事前設計**: 知識ベースはボトムアップで育つ。上から分類木を作ると空カードが量産される
- **「完全なクラスライブラリ」目標**: 知識に完成状態はない。枚数目標そのものがOOP比喩の誤用
- **多重継承的な過剰リンク**: 関係数がカード数の3〜4倍を超えたら関係型の粒度を疑う（現状 107/36 ≒ 3.0 は境界域）

## 2. 作成停止・拡張・統合のメトリクス（数値はすべて設計上の目安）

**作成停止シグナル（新規草案を止める）**
- 重複判定率: 直近10件の質問生成のうち既存カードへの追記で解決した割合が **70%超** → その領域は飽和
- 承認待ち滞留: `_inbox` の未承認が **承認済みの50%超** → 作成よりレビューに切替
- 孤立カード率: 関係0本のカードが **10%超** → 新規より接続作業

**拡張シグナル（作成再開）**
- 質問が既存カードで答えられない率が直近サイクルで **30%超**
- 特定カードへの参照集中: 1カードが全関係の **10%超** を占める → 概念が太りすぎ。分割候補

**統合シグナル**
- 2カード間の関係が「ほぼ同義」「常に共起」→ 二者レビュー（Fable 5 / GPT-6 Astra）に統合可否を回す
- 実例が0のまま **3レビューサイクル** 経過した概念カード → 統合または廃止候補としてユーザーに提示（独断削除しない）

## 3. 最小実行可能アーキテクチャ

```
concepts/          # 概念クラス層
  _inbox/          # AI草案（未承認）
  approved/        # ユーザー承認済みのみ
relations.md/db    # 関係層: 型付きリンク（is-a, uses, contrasts-with 等、型は5〜8種に制限）
examples/          # インスタンス層: 概念1つ以上を参照する具体事例
evidence/          # 根拠層: MIT OCW断片等の出典。カードは根拠IDを参照、本文にコピペしない
queries/           # 問い合わせログ: 自己生成質問・検索結果・重複判定の記録
```

各層の役割:
- **概念クラス**: スキーマ準拠の抽象定義。承認状態をフロントマターで明示
- **関係**: カード間のみ。型の新設は二者レビュー必須
- **実例**: 概念の「テストケース」。実例が付かない概念は仮説扱い
- **根拠**: 出典の一次置き場。1根拠が複数カードを支えてよい
- **問い合わせログ**: メトリクス計算の原データ。これがないと2の判断ができない

## 4. 36カードからの段階的目標（目安）

**フェーズ1（現在〜）: 承認消化**
新規作成を週数枚に絞り、既存36枚のユーザー承認を先行。目標: 承認済み比率 50%超

**フェーズ2: 接続と実例**
承認済みカードに実例を最低1つずつ付与。孤立カード0。カード数は **50枚前後** で一旦止める（根拠: 質問生成の重複率を測るのに十分なサンプルサイズという設計判断であり、実測で調整）

**フェーズ3: メトリクス駆動**
2のシグナルに従い拡張/統合。枚数上限は設けず、**「未回答質問率30%超で拡張」** をトリガーにする

**要点**: 「何枚作るか」ではなく「問い合わせログが示す不足に応じて作る」に判断基準を移すこと。枚数は結果指標であり目標にしない。
