## Definition
フィードバック制御とは、システムの**現在の出力を測定し、目標値との差分（誤差）を計算して、その誤差を最小化するよう入力を継続的に調整する仕組み**です。家の暖房で室温が下がるとヒーターが強くなり、上がると弱くなるのと同じ原理です。目的地への経路修正を繰り返す自動運転も本質的には同じクローズドループです。この「測定→比較→調整→再測定」のサイクルが、安定した動作を実現します。

## Mechanism
フィードバック制御の因果連鎖：

```
目標値(r) - 測定値(y) → 誤差(e = r - y) 
                ↓
          制御器(C) [例：PID則]
                ↓
          制御入力(u) → システム(P) 
                ↓
              出力(y) → 測定機構 → [上へループバック]
```

**PID制御則の自然言語説明**：
- **P（比例）成分**：誤差に比例した力を加える。誤差が大きいほど強く修正
- **I（積分）成分**：過去の誤差の累積を考慮。定常偏差を完全に消す
- **D（微分）成分**：誤差の変化速度を見て、行き過ぎを予防する制動

数学的には制御入力 `u(t) = Kp·e(t) + Ki·∫e(τ)dτ + Kd·de/dt`

この構造により、外乱が入ってもシステムが自動的に元の状態に戻ろうとします。

## Boundary Conditions
このフィードバック制御が効力を失う（壊れる）条件：

1. **測定遅延が大きい場合**：温度計の応答が5分遅れると、制御が過敏になり振動（オーバーシュート）が起きる
2. **非線形性が強い場合**：PIDパラメータを線形システム向けに調整したのに、実際のシステムが強い非線形性を持つと発散する可能性
3. **時間遅延が支配的**：制御信号を送ってから効果が現れるまでの遅延が大きいと、フィードバックが逆効果になる
4. **測定ノイズが大きい**：D項がノイズを増幅して振動を招く
5. **飽和制約**：制御入力に上限がある（ヒーターの最大出力など）のに、制御器が無限に大きな指令を出そうとする場合

## Failure Modes
誤適用時の観察可能なエラー：

- **オーバーシュート＆振動**：目標に向かって行き過ぎて、振動が続く。Dゲインが低すぎる典型症状
- **定常偏差の残存**：目標値に完全に到達しない。I成分が不足
- **制御入力の飽和に伴う不安定化**：最大値に張り付いたまま制御不能に
- **ノイズ増幅による粗い動き**：P/Dゲインが高すぎると、測定ノイズが制御信号に直接影響

## Business Transfer

### シナリオ1：SaaS提供企業のAPI応答時間最適化
**適用**：CloudサービスのCPU自動スケーリングで、レイテンシを目標値（例：100ms）に保つ。監視システムが応答時間を測定 → レイテンシが高ければインスタンス数を増やす（または減らす）。
**Caveat**：スケールアップに数分かかる場合、短期的な負荷スパイクには追従できず、振動的な挙動（スケールアップ→過剰→スケールダウン→不足）が生じやすい。起動時間を安定的に予測できないと制御ゲインの調整に失敗する。

### シナリオ2：SaaS課金システムの収益ターゲット達成
**適用**：月間目標収益に対して、実績を毎日測定し、進捗が遅れていれば営業チームの人数や施策を強化する。
**Caveat**：営業施策の効果が3週間後に出るなど、時間遅延が大きいと制御が逆効果になる。また、価格値上げなど非線形な施策を加えると従来の線形PIDモデルが破綻する。

### シナリオ3：製造業の在庫管理
**適用**：需要予測と実績の乖離を監視し、在庫が目標水準より多ければ発注を減らす。
**Caveat**：サプライチェーンの遅延（納期が変動する）があると、過去のフィードバックに基づいた制御が現在の状況に合わなくなる。季節変動が大きいモデルでは線形フィードバックは不十分。

## Non-Examples
似ているが異なる概念：

- **オープンループ制御**：「毎日同じ量の肥料を散布する」農業。現在の土壌状態を測定して調整しないため、外乱（雨）の影響を受けやすい
- **スケジュール駆動の計画実行**：「計画通りに予算を使う」財務管理。実績と目標の乖離を無視して進む
- **状態機械的な条件分岐**：「IF温度>30°C THEN停止」の単純if-then。フィードバックではなく固定的な閾値判定

## Definition
状態機械とは、**システムが離散的で有限の「状態」の集合の中に常に存在し、イベントや条件に応じて状態から状態へ遷移する枠組み**です。交差点の信号機（赤→青→黄→赤）、自動販売機（待機→商品選択→決済完了）、または会社の請求プロセス（未送信→送信済→支払済→完了）など、段階的に進む任意のプロセスを形式化できます。各状態では特定の動作が許可され、そうでない動作は拒否されます。

## Mechanism
状態機械の構造：

```
状態集合 Q = {q0, q1, q2, ...}
入力アルファベット Σ = {事象1, 事象2, ...}
遷移関数 δ: Q × Σ → Q
  例： δ(赤, タイマー満了) → 青

現在状態 q_current と入力 a に対して：
  q_next = δ(q_current, a)
```

**自然言語での実行メカニズム**：
1. システムがある状態（例：「支払待ち」）にいる
2. 外部イベント（例：「クレジットカード承認」）が発生
3. 遷移関数がこの (状態, イベント) の組を見て「次の状態は『完了』」と決定
4. システムは新しい状態に移行し、その状態での動作ルールが発動

状態ごとに異なるルールセットが存在することが本質：状態Aでは禁止されている操作が、状態Bでは許可される。

## Boundary Conditions
状態機械がモデリング能力を失う（壊れる）条件：

1. **状態数が爆発的に増える**：N個の独立した変数があると、状態数は2^N になる（状態爆発問題）。例えば、ユーザーの「ログイン/ログアウト」「プレミアム/通常」「アクティブ/非アクティブ」という3つの二値変数で8状態必要
2. **連続的な値や無限精度が必要**：温度制御で「温度は15.3456...°C」というように無限に微妙な値を状態として記録する必要がある場合、有限状態機械では不十分
3. **並列プロセスの相互作用**：複数のエージェントが独立に動く場合、状態の組み合わせが指数関数的に増える
4. **確率的な挙動が本質的**：「50%の確率で状態Aへ」という非決定論的遷移は基本的な有限状態機械では扱えない（確率的オートマトンが必要）
5. **無限の未来を考慮する必要がある場合**：「いつかは終了する」と保証できないシステム

## Failure Modes
不適切に状態機械を使った場合の観察可能な問題：

- **状態爆発による複雑さ**：保守不可能なほど多くの遷移ルールが必要になり、バグが増殖
- **デッドロック**：ある状態から脱出する遷移が存在しない（例：「キャンセル不可」なまま）
- **未定義の遷移**：予期したイベントに対する遷移ルールが存在せず、エラーになる
- **過度な単純化**：実際には「保留中」という曖昧な状態があるのに、「完了」と「未完了」の2状態しかモデル化しない

## Business Transfer

### シナリオ1：注文フルフィルメントパイプライン
**適用**：電商プラットフォームで注文ステータスを状態機械でモデル化：
- 状態：{未確認 → 支払確認 → ピック → パック → 発送 → 配達完了 → 返却可能 → 返却不可}
- イベント：支払完了、在庫確認、配達完了など
- 各状態でのルール：例えば「配達完了状態でのみ返却を受け付ける」
**Caveat**：複数商品の注文で各SKUが異なる状態遷移をしている場合、注文全体の状態を定義するのが複雑化する。「部分配達」という状態を追加するかどうかで状態数が大きく増える。

### シナリオ2：SaaS請求サイクル管理
**適用**：サブスクリプション企業で顧客アカウントのステータスを管理：
- 状態：{トライアル → アクティブ → キャンセル予定 → サスペンド → キャンセル完了}
- 遷移トリガー：カード有効期限切れ→サスペンド、キャンセル申請→キャンセル予定、など
**Caveat**：「一時停止中に再開」という操作が許可される場合、状態定義が曖昧になりやすい。また、同じ「サスペンド」状態でも理由（支払い失敗 vs 管理者による停止）が異なると、許可される操作が変わる可能性があり、隠れた状態が必要になる。

### シナリオ3：ワークフロー承認フロー
**適用**：経費精算ワークフローで申請の進行状況を追跡：
- 状態：{草稿 → 提出 → 一次承認待ち → 二次承認待ち → 却下（→草稿に戻る）→ 承認完了 → 支払い完了}
- イベント：「却下」で以前の状態に戻る（遷移の非単調性）
**Caveat**：複数の承認者が並列に同じドキュメントを承認する場合、「2人とも一次承認待ち中」という状態を正確にモデル化する必要がある。状態機械では基本的に単一の状態しか持てないため、こうした並列プロセスは一度に複数状態の組み合わせが必要になり、爆発的に複雑化する。

## Non-Examples

- **制御フロー（if-then-else）**：プログラムの条件分岐。状態が保持されず、毎回フレッシュに判定される
- **データベースのERモデル**：「ユーザーテーブル」のように多数の属性を持つもの。状態の列挙的な離散化ではなく、属性の組み合わせ
- **確率的プロセス**：遷移が決定論的ではなく、分布に従う（例：マルコフ連鎖では遷移確率が存在）
- **スケジューラ**：「9時に実行、10時に実行」といった時間ベースの制御。状態遷移ではなくタイムトリガー

## Definition
グラフ探索アルゴリズムとは、**ノード（頂点）とエッジ（辺）で構成されたグラフ構造において、開始点から目標点へ到達する経路を見つけたり、すべてのノードを訪問したりするための系統的な方法**です。都市間の最短ルート、ゲームの次の一手の選択肢、組織内のデータの依存関係の追跡など、「どこから始まり、次に何ができるか」という形式で表現できるほぼすべての問題に応用できます。BFS（幅優先）、DFS（深さ優先）、A*（最適コスト探索）の3つが古典的な手法です。

## Mechanism
各アルゴリズムの本質的な動作：

### BFS（幅優先探索）
```
未探索ノード集合: {全ノード}
現在の境界層 frontier = {開始ノード}

while frontier が空でない:
  frontier の全ノードを同時に処理
  各ノードの隣接未訪問ノードを新しい frontier に追加
  frontier を次の層に更新
```
**特性**：最初に見つかった経路は最短（エッジ数が少ない）。全ノードの距離を均一に調べる（幅広い視野）。

### DFS（深さ優先探索）
```
スタック stack = [開始ノード]

while スタックが空でない:
  ノード = stack.pop()
  未訪問なら訪問済みにマーク
  隣接ノードをスタックに push
```
**特性**：一本道を徹底的に掘り進み、行き止まったらバックトラック。メモリ効率が良い場合が多い。

### A*（最適経路探索）
```
評価関数: f(n) = g(n) + h(n)
  g(n) = 開始からノード n までの実際のコスト
  h(n) = ノード n から目標までの推定コスト（ヒューリスティック）

priority_queue = [開始ノード]

while キューが空でない:
  f(n) が最小なノードを取り出す
  目標なら終了
  隣接ノードを評価関数で評価し直し、キューに追加
```
**特性**：実現可能なコストと未来予測を組み合わせて効率的に最適解を探す。良いヒューリスティックがあれば爆発的に高速化。

各アルゴリズムの因果連鎖：
- 探索順序の選択（FIFO vs LIFO vs優先度順） → 訪問するノード数と順序 → 見つかる解の質（最短性）と探索速度

## Boundary Conditions
グラフ探索が効力を失う（壊れる）条件：

1. **グラフが無限**：インターネット上のすべてのWebページから特定のページを探すなど、事前にグラフ全体が見えない
2. **動的に変わるグラフ**：ソーシャルネットワークで「ユーザーをフォロー/フォロー解除」される最中に探索すると、訪問済みノードのエッジが消える可能性
3. **負のコスト（重み）が存在**：ダイクストラやA*は負の重みに対応せず、無限ループに陥る可能性
4. **ヒューリスティックが不正確**：A*は h(n) が実際のコストより大きいと、最適解を見逃す可能性
5. **状態空間が指数爆発**：ノード数が2^Nのような規模だと、メモリに乗らない

## Failure Modes
不適切に使った場合の観察可能な問題：

- **メモリ枯渇**：BFSで大規模グラフを探索すると、frontier の全ノードをメモリに保持する必要があり、枯渇
- **探索完了の遅延**：グラフが大きく、目標が遠い場合、DFSで運悪く反対方向を優先探索すると、見つけるまでに膨大な時間
- **最適解の喪失**：A*で不正なヒューリスティック（h(n) > 実際のコスト）を使うと、最短経路を見逃す
- **サイクルによる無限ループ**：訪問済みリストを管理しないと、グラフのサイクルで永遠に回り続ける

## Business Transfer

### シナリオ1：サプライチェーンのボトルネック検出
**適用**：製造工場から顧客への商品の流れを有向グラフで表現（工場 → 流通拠点A/B → 配送センター → 最終顧客）。BFSで各ステップの処理時間を測定し、最短ルートと実際のルートの差分を分析してボトルネック（予期しない遅延地点）を発見。
**Caveat**：複数のルートがあり、コスト（運送費、時間）が季節や曜日で動的に変わる場合、静的なグラフモデルでは不十分。A*を使う際に、正しい「推定コスト」を予測できないと、かえって効率が低下する可能性。

### シナリオ2：組織内の権限委譲チェーン
**適用**：経営層から現場までの報告・承認ラインを有向グラフで表現。DFSで特定の決定権（例：予算承認権）がどこまで委譲されているか、逆方向に追跡。
**Caveat**：マトリックス組織で複数の報告ラインが存在すると、グラフが複雑化し、探索が重複する。サイクル（AがBを評価し、BがAを評価する）が存在するとDFSで無限ループになりうる。

### シナリオ3：顧客の購買経路の最適化
**適用**：Webサイト内のページ遷移をグラフで表現（ホーム → 商品カテゴリ → 商品詳細 → カート → 支払い）。A*で「ユーザーが最短クリック数で購入に至る経路」を見つけ、現在のサイト設計がそれを阻害していないか検証。
**Caveat**：ユーザーの行動は確率的（ある確率でカテゴリAを選ぶ）であり、単一の「最適ルート」が存在しない。A*は決定論的な最短路を見つけるため、ユーザーセグメント（新規 vs リピーター）ごとに異なるヒューリスティックが必要になる。

## Non-Examples

- **線形探索**：リストの先頭から順に「Xが見つかるまで」チェック。グラフ構造（複数の次ステップ）がない
- **ランダムウォーク**：グラフをランダムに歩く。系統的でなく、効率が低い
- **動的計画法**：部分問題の最適解をキャッシュして再利用。探索ではなく、分割統治
- **シミュレーション**：グラフを構築せず、実際にシステムを動かして観察。事前計画ではなく事後分析

## Definition
確率的推論とは、**部分的で不完全な情報（観測）から、未観測の変数の確率分布を計算し、最も起こりやすい状態や行動を推奨するプロセス**です。ベイズネットワークは、この推論を効率的に行うための有向非巡回グラフで、各ノードは確率変数を、各エッジは「因果的な依存関係」を表します。医療診断（患者の症状から病気の確率を推定）、スパムフィルター（メールの特性から「スパムである確率」を計算）、自動運転（センサーノイズがある中で障害物の位置を推定）など、不確実性の下での意思決定が本質的なドメインで使われます。

## Mechanism
ベイズネットワークの推論メカニズム：

### 基本的な構造
```
ベイズネットワーク = 有向非巡回グラフ (DAG)
  各ノード: 確率変数 X_i
  各エッジ: 親ノード → 子ノード の因果関係
  各ノード: 条件付き確率表 (CPT) P(X_i | Parents(X_i))
```

### 推論の例：医療診断
```
親ノード: 病気D, 遺伝素因G
子ノード: 症状S1, S2

問題: 患者が症状S1と S2 を示している。
      病気Dを持つ確率 P(D | S1, S2) を計算せよ。

ベイズ則: P(D | S1, S2) = P(S1, S2 | D) · P(D) / P(S1, S2)

ネットワーク構造があると:
  P(S1, S2 | D, G) = P(S1 | D) · P(S2 | D)  [条件付き独立]
により、計算が劇的に単純化される
```

**自然言語での推論プロセス**：
1. **事前確率（Prior）**：何も観測する前の病気の基礎確率（例：全人口の5%が病気X）
2. **尤度（Likelihood）**：「病気Xなら症状Yが観測される確率」
3. **観測（Evidence）**：患者が実際に症状Yを示したという事実
4. **事後確率（Posterior）**：観測を踏まえた病気Xの更新確率（例：80%）

本質的には「新しい情報が入ったら、それまでの信念を理性的に更新する」という機械的なプロセス。

### 計算効率化の工夫
- **条件付き独立性**：グラフ構造から自動的に計算を省略できる変数の組を見つける
- **メッセージパッシング**：ノード間で局所的な確率情報を伝播させて、全体の事後確率を効率的に計算

## Boundary Conditions
ベイズネットワークがモデリング能力を失う条件：

1. **グラフ構造が未知**：変数間の因果関係が複雑で、正しいDAGが構築できない場合、推論は全く信頼できなくなる
2. **条件付き確率表が不正確**：P(症状 | 病気) の値を間違えて登録すると、推論結果は誤導される
3. **連続変数が必要**：「患者の血圧は120.5 mmHg」というように無限精度の連続値が必要な場合、離散的な確率表では不足
