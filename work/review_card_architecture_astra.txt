## 結論

**作る量は「クラスの数」ではなく、「対象の問いに、根拠付きで答えるための不足」で決める**のがよいです。まず36枚の新規追加を止めて評価し、必要なら40〜45枚へ進めます。107関係も、増やすこと自体は目標にしません。

以下の数値は、実測に基づく最適値ではなく、**小規模運用の初期ガードレール**です。

## 1. OOPを参照してよい部分・危険な部分

| 参照してよい設計原則 | 知識カードへの適用 |
|---|---|
| 単一責任・高凝集 | 1枚は、独立して説明・再利用できる知識単位にする |
| インターフェースの明示 | 定義、適用条件、何に使えるか、非適用例を記載する |
| 合成を優先 | 巨大なカードではなく、小さなカードを問い合わせ時に組み合わせる |
| 利用例から設計する | 先に問いと実例を置き、必要な抽象化だけを作る |
| テスト・リファクタリング | 問い合わせの回帰テストを持ち、分割・統合後も答えられるか確認する |

**危険なのは、知識をクラス階層に押し込むことです。**

- 概念だけでなく、命題・手法・モデルも知識単位になる。すべてを「クラス」にしない。
- `is_a` は厳密な下位分類に限定する。類似・部分・前提を継承で表現しない。
- プログラムの型と違い、知識には不確実性、例外、文脈依存、相反する根拠がある。
- 標準ライブラリのクラス数は、カード数の目安にならない。目的が違う。

したがって、**OOPは整理と変更の原則として借り、世界の分類体系としては借りすぎない**のが妥当です。

## 2. 作成停止・拡張・統合の判断

まず、対象用途を代表する**固定20問**を用意します。ユーザーの実際の問いを優先し、不足分だけ自己生成で補います。自己生成分の成績は別集計し、カード作成後に都合のよい問題へ差し替えません。

| 指標 | 定義・初期閾値 | 判断 |
|---|---|---|
| 根拠付き回答カバー率 | 既存カードで回答でき、原資料で根拠と適用条件を確認できる問い／20問。初期目標 **80%＝16問** | 到達後は網羅目的の追加をやめ、未解決需要に限定 |
| 反復する概念不足 | 同じ不足概念が、独立した問いで**2回以上**必要になる | 新規作成候補。検索不良・根拠不足なら既存側を改善 |
| 限界効用 | **最大3枚の追加**で新たに解けた評価問数 | **2回連続で1問以下**なら拡張を一旦停止し、設計を見直す |
| 重複候補 | 定義・適用範囲・問い合わせ上の役割が**3項目とも一致** | 統合を提案。文面や埋め込みの類似だけでは統合しない |
| 検証可能性 | 回答に使う主張・関係の出典箇所を追跡できる割合 | 確定回答に使う部分は**100%**を要件にする。未検証部分は明示して除外 |

重要な区別があります。

- カバー率は、**draftを含む「候補カバー率」**と、**ユーザー承認済みだけの「確定カバー率」**を分ける。
- 候補カバー率が高いのに確定カバー率が低いなら、必要なのは追加ではなく根拠確認・承認です。
- 停止は収集禁止ではなく、**新規カード化を止めて問い合わせログへ蓄積する**ことです。
- 高額レビューの待ち行列にも上限を設けます。例えば1周期5件と決め、満杯なら追加生成を止めます。

## 3. 最小実行可能なアーキテクチャ

Markdown＋JSONLで十分です。現段階ではグラフDBは必須ではありません。

| 要素 | 役割・最低限の内容 |
|---|---|
| **概念クラス／知識カード** `concepts/_inbox/K-XXXX.md` | 再利用単位。ID、種別〈概念・命題・手法など〉、定義、適用条件、非適用例、主張ID、状態 |
| **関係** `relations.jsonl` | 主語ID、関係型、目的語ID、適用条件、根拠ID、状態。初期は `is_a`・`part_of`・`requires`・`instance_of` 程度 |
| **実例** `examples/` | 現実・事業の具体的状況、対応する概念ID、適用結果、反例。抽象概念が本当に使えるか試す |
| **根拠** `evidence.jsonl` | URL、資料名、出典箇所、引用、取得日、支える／反する主張・関係ID、確認段階 |
| **問い合わせログ** `queries.jsonl` | 問い、実質問／自己生成、使用カード、回答可否、失敗原因、費用、レビュー結果 |

設計上の要点は次の3つです。

1. **根拠はカード全体だけでなく、個々の主張・関係に結び付ける。** MIT OCW検索断片は探索の手掛かりであり、原資料確認済みとは区別します。
2. **カード・関係ともに状態を持つ。** AIは `draft`／`needs_review` まで。`approved` への変更にはユーザー承認記録を必須にします。
3. 107関係を無理に型へ押し込まず、不明なものは保留します。関係数・平均次数を品質目標にしません。

## 4. 36枚からの低コストな次の目標

### 段階A：36枚のまま、使えるか測る
- 固定20問を作り、現状の候補／確定カバー率を測定。
- よく参照される**上位10枚程度**と、回答に必要な関係から原資料を確認。
- 失敗を「概念不足・根拠不足・検索不良・重複混乱」に分類。
- 統合は提案にとどめ、既存IDを削除しない。

### 段階B：不足が実証された場合だけ40〜45枚へ
- 反復して必要になった概念を、**1回最大3枚**追加。
- 各候補に「これで解けるようになる問い」を必須記載。
- 根拠追加や実例追加で済むなら、新規カードを作らない。
- 毎回カバー率と限界効用を再測定。条件を満たせば36枚で止めても成功です。

### 段階C：新しい用途が生まれた場合だけ50〜60枚を検討
- 既存用途の周辺を埋めるためではなく、未対応の事業・分野の問いが継続して現れた場合に限る。
- 新用途の評価問を追加してから、その不足分を作る。**50〜60枚は目標ノルマではありません。**

費用面では、ID・出典・重複候補の抽出を機械処理し、明確な既存カードへの根拠追記は通常経路へ。**曖昧な新規性・重複・関係型だけをFable 5とGPT-6 Astraの二者レビューへ送り、不一致は保留**します。二者一致も、原典確認やユーザー承認の代わりにはしません。

**次に増やすべきものはカードではなく、まず「20問の評価セット」と「失敗原因が分かるログ」です。**
