# 次ステップ計画レビュー

結論から言うと、大枠は妥当ですが、**順序の改善余地1点、アーキテクチャ違反1点、手戻りリスク3点**があります。順に述べます。

---## 1. B→C→Aの順序について

**基本方針は正しいが、Aの開始をPhase 2に前倒しできます。**

依存関係を整理すると:

- B（分野タグ）→ C後半（接続マップ）: **真の依存あり**。正しい。
- B → A（概念カード）: **依存なし**。Aは分野インデックスMDを読むだけで、検索システムを使わない。
- C前半 → A: **こちらに緩い依存がある**。これが見落とされています。

Aで「転用価値の高い概念」を抽出する際、**転用先＝4本柱が明文化されていないと、抽出基準がエージェントの主観になります**。C前半で4本柱MDが完成していれば、それを「抽出フィルタの仕様書」としてAgent4/5に渡せる。これで概念カードの選定基準が揃います。

**修正案:**
- Phase 1（並列）: B ＋ C前半（現行のまま）
- Phase 2（並列）: C後半 ＋ **A**（4本柱MDをフィルタ仕様として使用）

これで1フェーズ短縮でき、かつAの品質が上がります。

---

## 2. 分野インデックスのaccepted/配置は**アーキテクチャ違反です**

ご自身で書かれている通り、accepted/の定義は「一次資料で検証済みの主張単位」。分野インデックスMDは:

- AI生成の**要約・ナビゲーション資料**であり、主張単位ではない
- 一次資料（講義原文）との突合検証を経ていない
- 「カバー範囲」「ギャップ」等のメタ情報であり、知識そのものではない

このまま放置すると**accepted/の信頼性セマンティクスが崩壊します**。将来「accepted/にあるものは根拠として引用してよい」というルールでエージェントを動かすとき、AI生成サマリが根拠として混入する。これは4本柱②「決定論的コード×確率的AI」の思想そのものに反します（信頼レベルの型を縛るべき場所で縛れていない）。

**修正案:** 探索層に `maps/`（または `index/`）を新設して移動する。分野インデックスは「地図」であり、地図は探索層の道具です。accepted/には今後、「講義Xの第Y章にこの定理の証明がある」レベルの原子的・出典付き主張だけを入れる。

移動作業自体は軽い（Phase 1に混ぜられる）ので、今やるべきです。後回しにするほどaccepted/参照が増えて剥がせなくなります。

## 3. 概念カード4分野の選択について

**経済学・CSは必須。異論なし**（強みの経済×IT、4本柱すべてに直結）。

問題は残り2枠です。4本柱を要素分解すると:

| 柱 | 必要な学術基盤 |
|---|---|
| ①自己修復ループ | ソフトウェア工学、**制御理論（フィードバック）**、形式検証 |
| ②ハイブリッド制御 | **確率・統計**、ステートマシン＝オートマトン理論、制御理論 |
| ③次世代RAG | 情報検索、**線形代数・統計**、グラフ理論 |
| ④現実空間グラウンディング | 信号処理、CV、ロボティクス |

**数学・統計が3本の柱に横串で刺さっているのに、4分野に入っていません。** 特に②のハイブリッド制御は「確率的システムをどう決定論的枠に閉じ込めるか」という問題で、これは確率論・制御理論の古典的テーマです。MIT OCWの数学・EECS系講義はここが最も厚い領域のはず。

- 脳認知科学: 集合知・エージェント設計との接続はあるが、4本柱への直接寄与は薄い。**第2バッチに回す価値あり**
- 経営学: ビジネス応用の出口として妥当だが、MIT OCW（Sloan系）の講義ノートは概念の深さにばらつきがある。こちらも入替候補

**推奨:** 経済学・CS・**数学/統計**を確定枠とし、4枠目を経営学か脳認知科学で選ぶ。もしくは1分野あたりのカード数上限を設けて5分野にする（後述の理由でカード数上限はどのみち必要）。

## 4. エージェント割り振り

改善点3つ:

**(a) C後半が単一エージェントでボトルネック。** 4本柱は独立性が高いので、柱ごとに分割して2エージェント×2柱で並列化可能。Phase 2にAを前倒しするなら、ここの短縮効果は大きい。

**(b) モデルの割り当てが逆になるリスク。** 概念カードは知識基盤の中核資産で、下流（perspectives接続、outputs生成）すべてが依存します。ここにHaiku 4.5を使って抽象化の質が落ちると、手戻りが全下流に波及する。**概念カード抽出には強いモデル、Bの検索改修（機械的なコード作業）やタグ付けにHaikuを割り当てるべき**です。

**(c) レビュー工程が計画にない。** _inbox/→直下への昇格はユーザー確認とのことですが、4分野一斉に走らせるとinboxが溢れてレビューがボトルネック化します。対策:
- **パイロット先行**: 1分野10枚だけ作ってユーザーレビュー→テンプレとNG例を確定→残りをスケール
- 分野あたりカード数上限（20〜30枚）を仕様に入れる

## 5. 見落としているリスク・手戻りポイント

**最重要: 概念カードのスキーマが未定義。** Phase 3開始前に決めないと、Agent4と5でフォーマットが割れ、後から全カード書き直しになります。最低限: 概念名／一行定義／出典講義ID／関連する柱（①〜④タグ）／転用シナリオ／関連概念リンク。**特に出典講義への安定ID**を今決めること。ファイルパス参照にすると、フォルダ再編で全リンクが死にます。

**分類誤りの伝播。** 3モデル多数決の68件には誤分類が混じっている前提で動くべき。Bで分野タグを検索に載せると、誤分類がフィルタ結果に直接出ます。多数決が2:1だった案件だけでも抜き打ち検証を。

**概念の重複・別名問題。** ゲーム理論は経済学とCSの両方から出てきます。分野別に並列抽出すると重複カードが必ず発生する。マージルール（正規名＋エイリアス）を先に決めておく。

**接続マップの浅さ。** C後半で全文検索ベースの接続を作ると、キーワード一致の表層的なリンクが量産されるリスク。「GraphRAG」で検索してヒットした講義が本当にビジョンを支えるとは限らない。接続には「supports / 手法を提供 / ギャップを示す」等の**関係タイプ**を付け、人間レビューを通す。

**受け入れ基準の不在。** 「この知識基盤が使えるか」を測るクエリセット（例:「マルチエージェントの合意形成に使える理論は？」等10問）を先に定義し、各フェーズ完了時に叩く。これがないと「完成した気がする」で終わります。

## 6. 4本柱の接続方法について

**perspectives/に4本柱本体を置くのは正しい**です。柱は「ユーザー本人のビジョン＝問いと判断」なので層の定義に合致します。

改善すべきは**接続の構造**です。提案中の「柱→講義」直結マップには2つの問題があります:

1. 講義4,258本に直接リンクすると脆く、メンテ不能になる
2. Aで作る概念カードと役割が重複する

**推奨: 柱→概念カード→講義の三層リンクにする。** 概念カードを結合テーブルとして使い、柱は概念だけを参照する。講義への出典リンクは概念カード側が持つ。これなら講義側の変更が柱に波及しません。

さらに一歩進めるなら、この接続を散文MDではなく**軽量グラフ（YAML/JSONで node: 柱/概念/講義、edge: 関係タイプ）として持つ**こと。柱③がGraphRAGなのだから、自分の知識基盤の接続構造をグラフで持つのはドッグフーディングそのものです。将来のGraphRAG実装の最初のシードデータになります。
