## 総評

方向性は良いですが、現状の **B→C→Aの前に「Phase 0：スキーマ・評価・来歴管理」** が必要です。

特に危険なのは次の2点です。

1. **生成された分野インデックスが、検証済み根拠と同じ`accepted/`に入っている**
2. **分野インデックスという「要約の要約」から概念カードを量産しようとしている**

このまま進めると、検索・概念・根拠の区別が曖昧になり、後から「これはMITが言っているのか、AIがまとめたのか、ユーザーの判断なのか」を分離する作業が発生します。

推奨順序は以下です。

> **Phase 0 → BとC前半とA小規模パイロットを並列 → C後半 → A本展開**

---

# 1. B→C→Aの順序は正しいか

## 結論

**本展開の順序としては概ね正しい**です。

- BがないとCの接続精度・再現性が低い
- Cを先に行うと、Aで抽出すべき概念に優先順位を付けられる
- Aを先に全面展開すると、使わない概念カードを大量生産する可能性が高い

ただし、以下のように修正すべきです。

## 推奨工程

### Phase 0：先に決めるもの

1. 安定したID体系
   - `field_id`
   - `course_id`
   - `document_id`
   - `chunk_id`
   - `concept_id`
   - `perspective_id`
   - `claim_id`

2. 成果物スキーマ
   - 分野インデックス
   - perspective
   - 接続エッジ
   - 概念カード
   - accepted claim

3. 来歴情報
   - 生成モデル
   - 生成日時
   - プロンプト／ワークフロー版
   - 入力ソース
   - ソーススナップショット
   - 人間確認状態

4. 検索評価セット
   - 30～50件程度の代表クエリ
   - 分野指定あり／なし
   - 日本語クエリ／英語クエリ
   - 複数学問分野にまたがるクエリ
   - 取得すべき講義と取得してはいけない講義

評価セットなしでBを改修すると、「動いたが良くなったか分からない」状態になります。

---

### Phase 1：並列

#### Agent 1：Bの実装

単に検索結果に分野名を表示するだけでは不十分です。必要なのは以下です。

- SQL段階での分野フィルタ
- 安定した`field_id`による指定
- 表示名変更に影響されない設計
- 分野なし検索との後方互換性
- インデックス再構築手順
- 分類バージョンの記録
- 検索結果への`course_id`、`field_id`、ソースパス出力
- 可能なら複数分野タグへの対応

MIT講義には分野横断的なものがあるため、恒久設計としては、

```text
course 1 --- N course_field N --- 1 field
```

のような中間テーブルが安全です。現状は主分野1件でも、将来`primary/secondary`を追加できます。

#### Agent 2：C前半

4本柱をperspectivesに構造化する作業はBと並行可能です。ただし、AIがユーザーのperspectiveを勝手に確定してはいけません。

AIが作れるのはあくまで、

- 既存発言の構造化
- 不明点の抽出
- 仮説的な言い換え
- 確認質問

までです。

**C後半に入る前に、4本柱の内容をユーザーが確認するゲート**を置くべきです。

#### Agent 4または5：Aの小規模パイロット

A全体は待つべきですが、概念カードのスキーマ検証として10～20枚程度だけ先行してよいです。

目的は概念を増やすことではなく、

- 1枚の粒度
- 引用形式
- 重複判定
- 転用可能性の書き方
- failure modeの書き方
- どこまでを1概念とするか

を確定することです。

---

### Phase 2：C後半

Bの受入テスト完了後、4本柱とMIT講義の接続を作ります。

ただし、「関連講義一覧」だけでは弱いです。接続ごとに最低限、以下を持たせてください。

```yaml
from: perspective:P1
to: course:MIT-XXXX
relation: operationalizes
claim: "自己修復ループは、制御理論上のフィードバック系として整理できる"
source_locator: "lecture-07.md#..."
quote: "..."
confidence: medium
review_status: generated
```

`relation`は少なくとも以下を区別すべきです。

- `supports`：主張を根拠付ける
- `constrains`：成立条件や制約を与える
- `contradicts`：反証・緊張関係
- `operationalizes`：実装可能な形に落とす
- `analogy`：類推にすぎない
- `gap`：MIT側で不足している
- `example`：適用事例

「関連している」と「ビジョンを支持している」は別です。ここを混ぜると知識基盤の信頼性が下がります。

---

### Phase 3：A本展開

Cで見えた重要概念・不足概念を優先して抽出します。

つまり、

> 分野ごとに均等抽出するのではなく、4本柱との接続密度と転用価値で抽出する

方がよいです。

---

# 2. 分野インデックスをaccepted/に置くべきか

## 結論

**置くべきではありません。**

分野インデックスは以下が混ざった生成物です。

- ソース範囲の要約
- AIによる概念整理
- カバー範囲の判断
- ギャップ推定
- 他分野との接続推定

これは「検証済みの主張単位」ではなく、**派生したナビゲーション成果物**です。

## 推奨配置

例えば以下です。

```text
sources/
  mit_ocw/

indexes/
  fields/
  courses/

concepts/
  _inbox/
  ...

perspectives/
  drafts/
  confirmed/

claims/
  candidate/
  accepted/
  rejected/

links/
  generated/
  reviewed/

outputs/

_meta/
  manifests/
  schemas/
  evaluations/
```

現在の5層を大きく壊したくないなら、探索層の下に置いてもよいです。

```text
exploration/
  mit_ocw/
  development/
  indexes/
    fields/
```

## より本質的な問題

現在のアーキテクチャは、

- 成果物の種類
- 信頼状態
- 知識処理の段階

を同じディレクトリ階層で表そうとしています。

しかし本来、次の2軸は分けるべきです。

### 成果物タイプ

- source
- index
- concept
- perspective
- claim
- output

### 状態

- generated
- reviewed
- accepted
- rejected
- deprecated

したがって`accepted`は汎用レイヤーではなく、主として**claimの状態**にした方が明確です。

```text
claims/accepted/
```

分野インデックスは人間が確認済みになっても、あくまで、

```yaml
artifact_type: field_index
review_status: reviewed
```

であって、検証済みの一次主張にはなりません。

また、MIT OCW講義資料は有力な教育資料ですが、学術論文上の「一次研究」と同義ではありません。高リスクなビジネス判断に使う場合は、MIT資料から原典論文・標準規格・公式統計などへ遡る経路も必要です。

---

# 3. 概念カード抽出対象の4分野は妥当か

## 結論

**ユーザーの経歴・関心を表す4分野としては妥当ですが、4本柱を実装するための初期4分野としては最適ではありません。**

特に、

- 「経営学」は広すぎる
- 「脳認知科学」は重要だが、直近の柱1～3への寄与が相対的に弱い
- 制御理論・システム工学・OR・形式手法が不足している

という問題があります。

## 4本柱に必要な学術基盤

| 柱 | 主要な学術接続 |
|---|---|
| 1. 自己修復ループ | ソフトウェア工学、分散システム、制御理論、形式手法、信頼性工学 |
| 2. 決定論×確率的AI | 型理論、プログラミング言語、形式検証、統計、意思決定理論、AI安全 |
| 3. 次世代RAG | 情報検索、データベース、NLP、グラフ理論、機械学習、評価設計 |
| 4. 現実空間グラウンディング | ロボティクス、CV、信号処理、HCI、認知科学、センサー融合 |

## 推奨する第1波

35分野内に対応カテゴリがあるなら、次の4つを優先します。

1. **コンピュータサイエンス**
2. **経済学**
3. **システム・制御・OR**
4. **経営・組織行動・ネットワーク／集合知系**

脳認知科学は第2波でもよいです。

ただし、直近の最優先が柱3のRAGなら、4番目を統計・機械学習に替える方が実務的です。

## 分野単位より「概念クラス」単位がよい

実際には、分野ごとの枚数割当より以下のような横断テーマで抽出した方が価値があります。

- フィードバック制御
- 可観測性・可制御性
- フォールトトレランス
- メカニズムデザイン
- ゲーム理論
- インセンティブ整合性
- 集合知と情報集約
- 型と契約
- 形式検証
- 不確実性校正
- 探索と活用
- 情報検索評価
- グラフ上の伝播
- センサー融合
- 人間参加型制御

概念カード抽出の優先度は、例えば以下で決められます。

> 4本柱との関連度 × 再利用性 × 根拠密度 × ユーザー固有性 ÷ 抽出コスト

# 4. エージェント割り振りの改善点

## 現状案の問題

### 1. 生成担当ばかりで、独立検証担当がいない

Agent 4と5が大量の概念カードを並列生成すると、以下が起きます。

- 同じ概念を別名で作る
- 粒度が揃わない
- 引用形式が揃わない
- 「概念」と「手法」と「原則」が混ざる
- 分野ごとの文体差が固定化される

### 2. C前半をAIが確定してしまう危険

perspectivesはユーザー本人の判断層です。AIが整った文章を作るほど、本人が言っていない前提が紛れ込みやすくなります。

### 3. Bの担当範囲が軽く見積もられている

Bは「タグ表示」ではなく、

- DBスキーマ変更
- 移行
- 再索引
- 検索構文
- フィルタ
- テスト
- 既存機能の回帰確認

まで含むべきです。

## 推奨割り振り

### Phase 1

- **Agent 1：B実装**
  - スキーマ、移行、検索、CLI/API、再索引

- **Agent 2：B評価＋C前半**
  - 検索ゴールドセット作成
  - Bの独立テスト
  - 4本柱の構造化草案
  - ユーザー確認事項の抽出

- **Agent 4：概念カードのスキーマパイロット**
  - 10～20枚のみ
  - 本量産はしない

### 人間ゲート

- 4本柱の文章と前提をユーザーが確認
- 概念カードの粒度と形式を確認
- Bの検索品質を確認

### Phase 2

- **Agent 3：柱1・2の接続**
- **Agent 5：柱3・4の接続**
- **Agent 2：接続の独立検証**
  - 引用が実在するか
  - `supports`と`analogy`を混同していないか
  - 反証・制約を無視していないか

### Phase 3

- **Agent 4・5：概念抽出**
  - 分野ではなく、テーマバンドルで分担

- **Agent 3：重複統合・正規化**
  - canonical name
  - alias
  - parent/child
  - related concept
  - merge候補

## モデル選定について

GPT-5.6 LunaとHaiku 4.5を使うこと自体よりも、以下の役割分離が重要です。

- 強いモデル：構造化・統合・境界条件の記述
- 低コストモデル：候補抽出
- 決定論的コード：ID、引用位置、重複候補、スキーマ検証
- 別モデルまたは別プロンプト：独立検証

同一モデルによる生成と自己検証だけでは、相関した誤りが残ります。

# 5. 見落としているリスクと手戻りポイント

## 重要度が高いもの

### 1. 「要約の要約」問題

分野インデックスだけを読んで概念カードを作ると、

```text
講義資料
→ 講義Markdown
→ 分野インデックス
→ 概念カード
```

という多段圧縮になります。

概念カードは、分野インデックスをナビゲーションに使いつつ、最終的には講義本文の該当箇所まで戻って作るべきです。

---

### 2. 検索評価がない

Bの成功条件を定義してください。

例：

- 分野指定時に他分野が混ざらない
- 分野指定なしの既存結果を壊さない
- 全講義に`field_id`が付いている
- 不明分野を黙って欠落させない
- 日本語クエリでも英語概念へ到達できる
- 再索引しても同じ入力から同じ結果になる

SQLite FTSは英語資料に対する日本語クエリで弱くなりやすいため、少なくとも、

- 英日概念辞書
- クエリ展開
- perspectiveごとの英語キーワード
- 固有名詞・略称エイリアス

を検討すべきです。

---

### 3. 分野タグの単一分類

講義を1分野に固定すると、ゲーム理論、計算神経科学、組織設計、情報経済学などが取りこぼされます。

最初は主分野1つでよいですが、スキーマは最初から多対多にしておく方が安全です。

---

### 4. 概念の重複と粒度崩壊

典型例：

- feedback
- feedback loop
- negative feedback
- closed-loop control
- self-correction

これらを別カードにするか、親子関係にするかを決めないまま量産すると、後からの統合コストが高くなります。

概念カードには最低限、以下が必要です。

```yaml
concept_id:
canonical_name:
aliases:
definition:
mechanism:
assumptions:
boundary_conditions:
failure_modes:
business_transfer:
examples:
non_examples:
source_refs:
related_concepts:
status:
```

特に`boundary_conditions`と`failure_modes`が、このプロジェクトの目的である「雑な応用でミスらない」に直結します。

---

### 5. perspectiveへのAI由来内容の混入

AIが補った内容は必ず、

```yaml
authorship: ai_structured
user_confirmed: false
```

のように区別してください。

ユーザーが確認した後にのみ`confirmed`へ昇格させるべきです。

---

### 6. 「関連」と「根拠」の混同

MIT講義に似た話があることは、ビジョンが正しいことの証明ではありません。

接続には、

- 根拠
- 制約
- 反証
- 類推
- 実装手段
- 未解決ギャップ

を明示する必要があります。

---

### 7. インデックスの陳腐化

講義分類、Markdown、生成プロンプトのいずれかが変わると分野インデックスが古くなります。

各インデックスに入力マニフェストやハッシュを持たせ、

```yaml
source_snapshot:
taxonomy_version:
generator_version:
generated_at:
stale: false
```

を管理してください。

---

### 8. ライセンス

MIT OCW資料にはCCライセンスが付与されているものが多く、コースごとに条件確認が必要です。特に商用利用、引用、派生成果物、再配布の扱いは、ビジネス出力に進む前に整理すべきです。

概念や事実そのものと、資料の表現・図表・文章の再利用は分けて扱う必要があります。

---

### 9. GraphRAGの早期導入

現段階でGraphRAG基盤を大きく作る必要はありません。

まずSQLite上で、

- nodes
- edges
- claims
- citations

を管理し、Markdownをビューとして生成すれば十分です。

関係タイプと評価方法が固まる前にグラフDBを導入すると、誤ったエッジを高速に蓄積するだけになります。

---

# 6. 4本柱をperspectives/に入れる以外の方法

## 結論

4本柱のうち、**ユーザーの信念・問い・優先順位はperspectivesに置くべき**です。

ただし、4本柱の全情報をperspectives内に閉じ込めるべきではありません。

1本柱には少なくとも3種類の情報が混ざっています。

1. ユーザーの判断・信念
2. 実装対象となる構想・要件
3. 学術的根拠との接続

これらを分離してください。

## 推奨構造

### perspectives/

「なぜそう考えるか」「何を重視するか」を置く。

```text
perspectives/
  P001_spec_driven_agents.md
  P002_deterministic_probabilistic_control.md
  P003_next_generation_rag.md
  P004_physical_grounding.md
```

### initiatives/またはspecs/

実装構想、要件、成功指標を置く。

```text
initiatives/
  I001_self_healing_agent_loop.md
```

内容：

- ゴール
- 非ゴール
- 要件
- 成功指標
- リスク
- 未確定事項
- 実験計画

### links/またはmaps/

MIT講義・概念・claimとの接続を置く。

```text
links/
  P001_academic_map.yaml
```

### claims/

検証可能な主張を分離する。

```text
claims/
  candidate/
  accepted/
  rejected/
```

## 最小限のグラフ構造

専用グラフDBはまだ不要です。SQLiteで以下を持てば十分です。

```text
nodes(
  node_id,
  node_type,
  path,
  status,
  version
)

edges(
  edge_id,
  from_node,
  to_node,
  relation_type,
  claim_id,
  confidence,
  review_status
)

citations(
  claim_id,
  source_id,
  locator,
  quote
)
```

Markdownは人間向け表示、SQLiteは機械向け正本という分担が扱いやすいです。

# 最終推奨プラン

## PR 0：基盤契約

- ID体系
- YAML front matter
- artifact typeとreview statusの分離
- 検索評価セット
- concept／perspective／claim／edgeのスキーマ
- 分野インデックスを`indexes/fields`へ移動
- 既存RAGへの互換パスまたは再索引

## PR 1：B

- 分野タグDB化
- SQLフィルタ
- CLI/API対応
- 複数分野対応可能なスキーマ
- 回帰テスト
- 日本語→英語クエリの最低限の展開

## PR 2：C前半

- 4本柱の構造化
- AI補完部分の明示
- ユーザー確認
- 1柱1ファイル＋全体overview

## PR 3：C後半パイロット

まず2本柱だけ接続し、以下を検証します。

- relation typeが十分か
- 引用粒度が適切か
- 反証・制約を拾えているか
- 分野フィルタが本当に有効か

問題なければ残り2本へ展開します。

## PR 4：Aパイロット

- 20枚程度
- 講義本文まで戻って引用
- 重複統合
- ユーザーが粒度を承認

## PR 5：A本展開

分野別ではなく、4本柱との関連度順に抽出します。

---

## 最終判断

- **B→C→Aという大方向は正しい**
- ただし、**Phase 0なしで進めるのは危険**
- 分野インデックスは`accepted/`から出すべき
- 現在の4分野は悪くないが、脳認知科学よりシステム・制御・ORを先行させる余地が大きい
- エージェントは生成担当だけでなく、独立検証・重複統合担当を置くべき
- 4本柱はperspectivesに置きつつ、実装仕様と学術接続は別成果物に分離すべき

このプロジェクトで最も重要なのは、知識量を増やすことではなく、**「誰が何を言ったのか」「何が根拠で、何が類推か」「どの条件下で転用できるか」を壊さず保持すること**です。
