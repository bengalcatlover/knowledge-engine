# あきらぐ コーディングガイドライン

> 配置先：`CODING_GUIDELINES.md`  
> 対象：本プロジェクトのすべてのソースコード、設定、テスト、運用スクリプト、公開物  
> 原則：**秘密を保存しない・依存を局所化する・変更を戻せるようにする・動作確認してから共有する**

本文の「必須」「禁止」はマージ・リリース・外部共有の条件とする。

記載するディレクトリやコマンドのうち、現在存在しないものは導入対象である。**ルールを文書化しただけでは、実装・検証済みと扱わない。**

---

## 1. 最優先ルール

1. **APIキー・認証情報をソースコード、Git、ログ、テストデータに残さない。**
2. **空の環境変数でAPI呼び出しを開始しない。設定不足は起動時に検出する。**
3. **LLMプロバイダー固有の処理を業務ロジックに書かない。**
4. **変更前に復旧地点を作り、1つの目的ごとに変更・検証・コミットする。**
5. **名前変更、処理変更、設定変更、DB変更を一括で実施しない。**
6. **失敗を空配列・成功・「知識が見つからなかった」に変換しない。**
7. **テスト未実施・実API未確認を「動作確認済み」と報告しない。**
8. **コードのロールバックと、DB・外部API副作用の復旧を別に考える。**
9. **自律処理は、予算・停止条件・設定検証が有効な状態でのみ動かす。**
10. **外部共有は、作業ディレクトリのコピーではなく、検査済みの公開物で行う。**

---

## 2. 現状からの復旧手順

現在は「大量変更後、環境変数不足でAPIが動かない可能性がある」状態である。追加の名称変更より、以下を優先する。

### 2.1 自動処理を停止する

- `autonomous_orchestrator.py`、`frontier_manager.py`、バッチワーカーの定期実行・再試行を止める。
- 動作不明なコードを本番DBに対して実行しない。
- 可視化が必要な場合は、読み取り専用・外部API呼び出しなしで起動する。

### 2.2 ハードコードされていたキーを失効・再発行する

- ソースから削除しただけで対応完了にしない。
- ハードコードされていたキーは漏えいした可能性があるものとして扱う。
- プロバイダー側の利用履歴・請求・異常アクセスを確認する。
- 新しいキーはコードに書かず、実行環境のシークレットとして設定する。

### 2.3 現在の状態を保全する

- 現在のコードとDBを、アクセス制限・暗号化された場所に保全する。
- 既存キーを含む可能性がある保全物を、Gitや共有フォルダに置かない。
- 保存先・作成日時・削除期限を記録する。
- 稼働中のSQLiteは、単純なファイルコピーではなくSQLite Backup API等で整合性のあるバックアップを取得する。

### 2.4 最小限の修正で動作を回復する

以下を一覧化する。

| 項目 | 記録する内容 |
|---|---|
| 呼び出し元 | モジュール・関数 |
| 処理上の役割 | claim生成、claim抽出、関係検証、バッチ等 |
| 使用設定 | プロファイル、環境変数名 |
| 接続実装 | 使用するアダプター |
| 状態 | 未確認／設定確認済み／モック確認済み／実API確認済み |

最初の修正は、設定の読み込み・空値検出・呼び出し経路の回復に限定する。名称統一やフォルダ移動は別変更とする。

### 2.5 秘密を除去してからGit管理を開始する

- 初回コミット前に、作業ツリーをシークレットスキャンする。
- `.gitignore`を作成してから、対象ファイルを明示してステージする。
- 初回は`git add .`や`git add -A`を使わない。
- 初回コミットには、判明している不具合と未確認項目も記録する。
- 未検証の初回コミットに「正常版」「安定版」という名前を付けない。

## 3. シークレット管理

### 3.1 保存場所

| 情報 | 許可する保存場所 | 禁止する保存場所 |
|---|---|---|
| APIキー、認証トークン | Secret Manager、CIのsecret、ローカルの未追跡`.env` | `.py`、追跡対象設定、README、テスト |
| ローカル設定 | 未追跡`.env`、アクセス制限された設定 | 外部共有物 |
| 設定項目の見本 | `.env.example` | 実値入りのサンプル |
| テスト用認証値 | 明らかなダミー値 | 実キーの一部・過去の実キー |

- 本番・開発・CIのキーを分離する。
- 最小権限・利用上限を設定する。利用可能な場合は短命な認証情報を使う。
- 認証情報をURLのクエリやCLI引数に渡さない。履歴・プロセス一覧・アクセスログに残るためである。

### 3.2 設定は一か所で検証する

環境変数の取得は`config/settings.py`等に集約する。各モジュールで独自に`os.getenv()`を呼んで設定判断をしない。

**禁止例：**

```python
api_key = os.getenv("LLM_PRIMARY_API_KEY", "")
client = SomeClient(api_key=api_key)
```

**必須動作：**

- 未定義・空文字・空白のみを区別せず「未設定」として拒否する。
- 使用するプロファイルに必要なアダプター・モデル・認証情報を検証する。
- 検証は、自律ループ開始・ジョブ取得・DB更新より前に行う。
- エラーには環境変数名と対処方法を表示し、値は表示しない。
- SDKが別の環境変数やローカル認証へ暗黙にフォールバックする場合、その挙動を無効化または明示管理する。

例：

```text
ConfigurationError:
LLM_PRIMARY_API_KEY が未設定です。
.env.example を参照し、実行環境に設定してください。
```

読み取り専用表示、検索のみ、ローカルembeddingなど、認証が不要な機能にまでAPIキーを要求しない。**有効化された機能に必要な設定だけを検証する。**

### 3.3 `.env.example`

追跡する見本には実値を入れない。

```dotenv
# テンプレート。空欄のままオンライン実行はできない。
LLM_PRIMARY_ADAPTER=
LLM_PRIMARY_MODEL=
LLM_PRIMARY_API_KEY=
```

- 使用可能なアダプター識別子と設定方法は運用文書に記載する。
- `.env`は自動的に読み込まれるとは限らない。ローカル開発時の読み込み方法を明記する。
- 本番では作業ディレクトリに偶然存在する`.env`へ依存しない。

### 3.4 ログと例外

以下をログ出力しない。

- APIキー、Authorizationヘッダー
- 環境変数の全件
- 認証情報を含むクライアント設定
- プロンプト・応答・HTTP本文の無条件な全文
- 秘密を含む可能性があるSDK例外の無加工出力

SDKのデバッグログは本番で無効にする。例外・ログのマスキングにはテストを設ける。

### 3.5 漏えい時

1. 対象キーを失効する。
2. 利用履歴と影響範囲を確認する。
3. ソース、ログ、成果物、Git履歴からの除去を行う。
4. 再発行したキーで復旧する。
5. 原因と防止策を記録する。

Git履歴の書き換えだけでは漏えい対応は完了しない。外部に渡ったコピーから回収できる保証はない。

## 4. AI抽象化：名前を消すのではなく、依存を境界に閉じ込める

### 4.1 抽象化の目的

目的は、プロバイダー変更時の影響範囲を限定し、業務処理を安定させることである。

**AI利用の事実、外部送信、利用条件まで隠すことを目的にしない。**

### 4.2 依存方向

```text
業務モジュール
    ↓
アプリケーション共通のLLM契約
    ↓
プロバイダーアダプター
    ↓
SDK / HTTP API
```

- 業務モジュールからプロバイダーSDKを直接importしない。
- SDK固有の応答オブジェクト・例外を業務モジュールへ渡さない。
- プロバイダーごとのJSON差異、認証方式、レート制限情報はアダプターで吸収する。
- JSON出力などの必須能力を満たさないプロファイルは、実行前に拒否する。
- 未対応機能を、知らないうちに別方式へ置き換えない。

### 4.3 命名規則

変数名・関数名は、会社名やモデル名ではなく**処理の役割**で付ける。

| 避ける名称 | 推奨する名称 |
|---|---|
| `claude_client` | `claim_generator`、`llm_client` |
| `call_gemini()` | `extract_claims()`、`generate_text()` |
| `haiku_worker` | `batch_worker` |
| `gpt_response` | `generation_result` |
| `use_astra` | `speech_profile` |

`ai1`、`engine_x`のような、意味を失わせる置換も禁止する。

- `cheap_llm.py`は将来的に`batch_llm_worker.py`等へ整理してよいが、設定修復と同時に変更しない。
- `ask_llm.py`も共通クライアントを利用する。例外的な直接API呼び出し経路にしない。

### 4.4 固有名を置いてよい場所

プロバイダー・モデル固有名は、以下に限定する。

- `llm/adapters/`内の接続実装
- 実モデルを選択する設定・モデルレジストリ
- アダプターのテスト・契約上の注意事項
- 依存関係ファイル、ロックファイル
- 運用文書、ライセンス表記、必要な出自情報

業務コードのコメントは「何のために呼ぶか」を説明する。

```python
# NG: 特定モデルでclaimを生成する
# OK: 文献照合前の候補claimを生成する。生成結果だけでは登録しない。
```

一方、アダプター内の固有仕様を説明するコメントは、正確な会社名・モデル名を使ってよい。

**SDK名、正式なモデルID、URL、JSONキー、ライセンス表記を一括置換してはいけない。**

### 4.5 設定は「役割 → プロファイル → 接続先」で解決する

役割の例：

- `claim_generation`
- `claim_extraction`
- `relation_validation`
- `batch_processing`
- `embedding`

業務コードは役割だけを指定する。モデル・認証情報・接続先は設定層で解決する。

- 同じプロファイルを複数の役割で利用してよい。
- バッチ用プロファイルが未設定なら、明示的な共有設定がない限り他へフォールバックしない。
- embeddingは文章生成と別契約にする。ローカル実行の場合はAPIキーを必須にしない。
- モデル名・プロンプト版・パラメーターの変更も、品質に影響する変更としてレビューする。

### 4.6 共通契約に含める事項

- 入力：役割、メッセージ、出力スキーマ、タイムアウト、出力上限
- 出力：正規化済み内容、終了理由、usage、request ID
- 失敗：設定不備、認証失敗、レート制限、タイムアウト、形式不正、予算超過
- 制約：空応答、途中切れ、不正JSONを成功扱いしない
- usage不明・料金不明をゼロとして扱わない

## 5. Git運用

### 5.1 基本ルール

- すべてのコード変更をGit管理する。
- `main`はオフライン必須テストが通る状態を維持する。
- 作業は`fix/...`、`refactor/...`、`feat/...`等の短命ブランチで行う。
- 個人開発でも差分確認とチェック結果を残す。
- 共有ブランチへのforce pushは禁止する。秘密除去等の例外は手順と影響を記録する。

### 5.2 コミット粒度

**1コミット = 1つの目的 = 独立してレビュー・取り消しできる変更。**

推奨例：

```text
fix(config): 空のAPIキーを起動時に拒否
test(llm): 設定欠落の回帰テストを追加
refactor(llm): バッチ呼び出しを共通クライアントへ移行
docs(ops): 実APIスモークテスト手順を追加
```

以下は分離する。

- 機械的なリネームと挙動変更
- フォーマット変更と機能追加
- DBスキーマ変更と検索方式変更
- プロバイダー変更とプロンプト変更

### 5.3 変更前の保護

- `git status`で既存の未コミット変更を確認する。
- 秘密検査後、既存作業を別コミットまたは適切なブランチに保護する。
- 大規模変更前には検証済みコミットに復旧用タグを付ける。
- DBバックアップはGitタグとは別に取得する。

`git reset --hard`、`git clean -fd`等は、未保存ファイル・未追跡データが失われないことを確認するまで実行しない。

AIコーディング支援にも、確認なしの破壊的Git操作・本番DB操作を許可しない。

### 5.4 コード復旧

共有済み変更の取り消しは原則`git revert`を使う。

ただし、以下はコードを戻しても元に戻らない。

- DBスキーマ・登録データ
- embeddingインデックス
- API利用料金
- 実行済みの外部処理

PRまたは変更記録に、それぞれの復旧方法を記載する。

## 6. 大規模変更の手順

次のいずれかに該当する変更を大規模変更として扱う。

- 複数の業務モジュールを横断する変更
- LLM設定・共通契約・SDKの変更
- 一括置換、フォルダ移動、公開APIのリネーム
- SQLiteスキーマ・検索インデックスの変更
- 予算制御・再試行・サーキットブレーカーの変更

### 必須手順

1. **変更計画を書く**  
   目的、対象、変更しないもの、リスク、確認方法、復旧方法を記載する。

2. **基準状態を確認する**  
   既存テストを実行し、既存の失敗と新規の失敗を区別する。  
   テストがなければ、正常と判断できる挙動から最小限の回帰テストを作る。

3. **復旧地点を作る**  
   コミット、必要なタグ、整合性のあるDBバックアップを用意する。

4. **最小の対象に適用する**  
   共通境界を作り、まず1つの呼び出し元だけ移行する。  
   最初から12モジュールすべてを変更しない。

5. **差分とテストを確認する**  
   import、CLI、設定名、例外、保存形式、ログ、副作用を確認する。

6. **段階的に展開する**  
   一時DB・固定データで検証し、必要に応じて承認済み実APIテストを行う。

7. **残りを移行する**  
   各段階でコミットし、旧経路は利用箇所がなくなってから削除する。

### 一括置換の制約

一括置換は対象一覧と差分を確認できる機械的変更に限る。

- 業務上の意味やSDK仕様を変える文字列置換は禁止。
- コメント、文字列、識別子を同じ置換規則で処理しない。
- 変更後はimport・CLI起動・設定検証・契約テストを行う。
- 検証のために新旧LLMを二重呼び出しする場合も、費用と外部送信の承認が必要。

## 7. テスト方針

### 7.1 テストの層を分ける

| 種類 | 保証するもの | 実API |
|---|---|---|
| 静的検査 | 構文、import、型、禁止依存、秘密混入 | 不要 |
| 単体テスト | 個別ロジック、例外、境界値 | 使用禁止 |
| 契約テスト | 呼び出し元と実装の入出力・失敗条件 | 原則不要 |
| 統合テスト | SQLite・複数モジュールの接続 | 原則不要 |
| スモークテスト | 現在の認証・モデル・接続先での最小動作 | 必要 |
| 品質回帰テスト | claim品質、検索品質、関係判定品質 | 固定評価セットで別管理 |

通常のテストはネットワークを遮断し、APIキーなしで実行可能にする。HTTP、LLM、文献検索、embedding取得を含む外部接続は明示的に置き換える。

### 7.2 契約テストの位置づけ

契約テストは**アダプター交換や内部リファクタリングの安全網**であり、実API疎通や知識の正しさの代わりではない。

同じ契約テスト群を各アダプターに適用し、少なくとも以下を確認する。

- 正常応答の正規化
- 必須フィールド不足、不正JSON、空応答、途中切れ
- 認証失敗、タイムアウト、レート制限
- 再試行回数の上限
- usage・request IDの扱い
- エラー文やログへの秘密混入
- 成功応答と失敗応答の区別

保存した応答fixtureは認証情報・非公開入力を除去し、API仕様・取得時期を記録する。

### 7.3 モジュール別の必須テスト

| モジュール | 最低限の確認事項 |
|---|---|
| `mvp_store.py` | トランザクション、外部キー、重複防止、policy拒否、途中失敗時のロールバック |
| `knowledge_amplifier.py` | claim・DOIの構造、既存4層検証の各拒否経路、登録条件、来歴保持 |
| `evidence_miner.py` | abstract欠落、抽出形式不正、根拠との対応、帰属不能時の処理 |
| `gap_detector.py` | G1/G2/G3の境界条件、auto-linkingの条件、再実行時の重複防止 |
| `node_factory.py` | unresolvedからの生成条件、重複ノード防止、部分失敗からの再実行 |
| `relation_engine.py` | co-evidence候補化、LLM検証失敗、自己辺・重複辺、方向・型の整合性 |
| `autonomous_orchestrator.py` | 7フェーズの順序、停止・再開、予算枯渇、再試行、サーキットブレーカー |
| `frontier_manager.py` | 深掘り・拡大の選択条件、探索上限、同一対象の無限反復防止 |
| `graph_server.py` | 起動、APIスキーマ、空DB、文字列の安全な表示、秘密の非表示 |
| `cheap_llm.py` | バッチ分割、部分失敗、応答件数の不一致、重複実行、予算 |
| `search_engine.py` | BM25、embedding、RRF、空検索、次元不一致、順位と同点時の扱い |
| `ask_llm.py` | 引数検証、設定不足、共通クライアント利用、失敗時の非ゼロ終了 |

既存の「4層検証」「G1/G2/G3」「7フェーズ」は、その名称・条件・状態遷移を文書化してからテストに固定する。名称から仕様を推測して書き換えない。

### 7.4 実APIスモークテスト

- 通常のCIから自動実行しない。
- 手動承認または専用の制限されたジョブで実行する。
- 合成データを使い、本番のclaim・abstract・DBを使用しない。
- リクエスト数、タイムアウト、出力上限、費用上限を設定する。
- 対象の役割・プロファイル・実行日時・コミットを記録する。
- 本番SQLiteには書き込まない。
- キー未設定時のスキップを「成功」と報告しない。

**モックテスト成功は実API動作の証明ではなく、実API成功は知識品質の証明でもない。**

## 8. 実行コマンドとマージ条件

以下の入口を整備する。内部で使うツールとバージョンは固定する。

| コマンド | 内容 |
|---|---|
| `make check` | lint、型検査、秘密検査、禁止依存検査、オフラインテスト |
| `make test-contract` | 共通LLM契約・主要データ契約のテスト |
| `make check-config` | 有効機能の設定検証。通信・DB更新なし |
| `make smoke-offline` | 一時DBと偽アダプターで主要フローを実行 |
| `make smoke-live` | 明示指定したプロファイルだけで実API確認 |
| `make release-check` | 外部共有物の秘密・データ・構成・起動手順を確認 |

オンラインテストの実行例：

```bash
make smoke-live \
  ROLE=claim_generation \
  PROFILE=primary \
  MAX_COST_USD=0.10
```

上限は例であり、実料金とリクエスト上限を確認して設定する。料金を見積もれない場合は実行を拒否する。

### マージ・リリース条件

- すべての変更：`make check`が成功していること。
- LLM共通契約の変更：契約テストが成功していること。
- 認証・接続先・モデル・SDKの変更：リリース前に該当プロファイルの実API確認があること。
- DB変更：旧スキーマからの移行・失敗時復旧を確認していること。
- 外部共有：公開物そのものに対する`release-check`が成功していること。

## 10. 本プロジェクト固有の安全ルール

### 10.1 LLM出力は「候補」であり「根拠」ではない

- LLMが生成したclaim・DOI・関係を、そのまま検証済みにしない。
- DOIの形式が正しいだけで、実在・内容一致・claim支持を確認したことにしない。
- 文献取得不能は、反証や検証成功ではなく「未確認」とする。
- 4層検証の短絡・省略は、ポリシー変更として扱う。
- co-evidenceを因果関係や独立した複数根拠と同一視しない。
- 生成したclaimが別経路で再入力されても、独立した証拠として数えない。

保存時には、根拠ID、検証状態、検証理由、実行ID、生成・検証に用いた設定版を追跡可能にする。秘密は保存しない。

### 10.2 policy engineを迂回しない

- 登録・更新は`mvp_store.py`の承認されたAPIを経由する。
- 他モジュールが直接SQLでclaim・node・edgeを追加して、policyを飛ばすことを禁止する。
- 候補・未確認・検証済み・拒否を区別し、検索・表示もその状態を尊重する。

### 10.3 DBトランザクション内で外部APIを待たない

原則：

```text
必要データを読む
    → 外部API・検証を実行
    → 更新条件を再確認
    → 短いトランザクションで登録
```

- 長時間のLLM呼び出し中にSQLiteの書き込みロックを保持しない。
- 外部キーの有効化、ロック待ち、並行書き込み方針を明示する。
- DB移行にはバージョンを付ける。
- バックアップは取得だけでなく、復元手順もテストする。

### 10.4 自律処理の予算は共有状態として管理する

`autonomous_orchestrator.py`、`frontier_manager.py`、バッチワーカーは、共通の予算管理を利用する。

- 呼び出し前に費用を予約し、結果で精算する。
- 再試行・フォールバック・並列呼び出しも予算に含める。
- 複数ワーカーが同じ残額を使い切らないよう、予約を原子的に行う。
- 結果不明のタイムアウトを「未課金」と決めつけない。
- 再起動によって実行予算や停止状態を無条件にリセットしない。
- アプリ側の推定だけに頼らず、可能な限りプロバイダー側の利用上限も設定する。

上限に達したら停止または明示的な保留にする。無制限モードへ移行しない。

### 10.5 再試行とサーキットブレーカー

- 未設定、認証失敗、無効なモデル指定は原則再試行しない。
- 一時障害・レート制限のみ、上限付きバックオフで再試行する。
- SDKとアプリの二重再試行を避ける。
- 試行回数だけでなく総経過時間も制限する。
- サーキットブレーカーが開いたとき、別モジュールが直接呼び出して迂回しない。

claim・node・edgeの登録には、用途に応じた一意制約や冪等性キーを用いる。処理再開で重複登録しない。

### 10.6 フェーズ失敗を隠さない

7フェーズの結果は少なくとも次を区別する。

- 成功
- 正常に処理したが対象なし
- 明示的にスキップ
- 再試行可能な失敗
- 設定・認証等による停止
- 予算による停止

`except Exception: return []`は禁止する。LLM停止を「gapなし」「claimなし」「探索完了」と表示しない。

### 10.7 検索インデックスは版管理する

`search_engine.py`では以下をインデックスのメタデータとして保持する。

- embeddingモデル・次元・正規化方式
- テキスト前処理・分割方式
- BM25のトークナイズ条件
- RRFの設定
- 対象DBまたはデータの版

embeddingモデル変更時は既存ベクトルと混在させない。再構築・切り替え・復旧手順を用意する。次元が同じでも互換とは限らない。

### 10.8 可視化サーバーは公開APIとして扱う

- `graph_server.py`は標準でlocalhostにバインドする。
- 外部公開には認証、アクセス制御、通信保護を設ける。
- CORSを無条件で全許可しない。
- claim・abstract・LLM出力は未信頼文字列としてエスケープする。
- 可視化経由の自律処理開始や設定変更には、閲覧とは別の権限を設ける。

### 10.9 文献・LLM出力を命令として実行しない

abstract、取得ページ、claim、LLM応答は未信頼データである。

- 内容に含まれる指示で設定・送信先・予算・policyを変更しない。
- LLM出力から任意SQL・Python・シェルを実行しない。
- 外部送信する情報を最小化し、非公開データの利用条件を確認する。

## 12. 導入順序

一度にすべてをリファクタリングしない。以下の順序で導入する。

1. **露出キーの失効、自律処理停止、コードとDBの保全**
2. **設定不足の検出と最小限のAPI経路修復**
3. **秘密除去、`.gitignore`整備、Git管理開始**
4. **主要フローのオフライン回帰テスト**
5. **共通LLM契約とアダプター導入、呼び出し元の段階移行**
6. **予算・再試行・DB更新・停止状態の契約テスト**
7. **CI・公開物検査・外部共有手順の整備**
8. **必要な名称整理・フォルダ再構成**

**最優先は「AIらしい名前を消すこと」ではなく、「秘密がなく、設定が明確で、動作を確認でき、変更を戻せる状態にすること」である。**
