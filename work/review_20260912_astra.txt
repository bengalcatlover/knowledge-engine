Q1_direction:
  decision: revise
  rationale: >-
    「LLMを提案者、基盤を構造・制約・由来・承認状態の管理者とする」方向は正しい。
    OOP層と探索的cell層の分離、候補層、人間承認、UIからのモデル変更も整合している。
    ただしOOPは実装・モジュール化の方式であって、推論の健全性を保証する形式体系ではない。
    中核を「OOP」単独ではなく、版付き原子主張、適用範囲、根拠、導出、実行可能モデル、
    依存失効を持つ型付き知識グラフとして定義し直すべきである。
    また5層は全知識が必ず直列通過する存在論ではなく、主張種別ごとに異なる根拠経路を持つ
    ガバナンス／抽象化ビューとして扱う必要がある。修正すれば致命的な見落としはない。
  blind_spots:
    - >-
      意味関係、根拠関係、導出依存、実装依存が同じ「エッジ」として混同される危険がある。
      エッジごとに推論効果と失効伝播規則が必要。
    - >-
      形式定理、経験的法則、シミュレーション結果、参考文献取り込みでは必要な根拠が異なる。
      全ノードに同一の5層根拠経路を要求してはいけない。
    - >-
      cell層の共活性化は発見候補でしかなく、意味的関連・因果・合成可能性を証明しない。
      検索順位や露出による共活性化バイアスも補正対象となる。
    - >-
      UIで任意ノードを差し替えてLLMに説明を再生成させるだけでは推論シミュレーションにならない。
      型検査、実行器、依存DAG、差分計算、反例検査を通る操作だけを許可すべきである。
    - >-
      「無限資金ならマーチンゲール成立」のような例はそのまま公理化できない。
      資金制約を外しても負の期待値は反転せず、停止時刻や期待賭け金が未定義・発散し得るため、
      前提変更後は決定的計算または証明で再評価する必要がある。
    - >-
      確信度を根拠経路数だけから計算してはいけない。同一起源、依存性、反証、適用範囲、
      校正履歴を扱えない間は離散的な認識状態を表示する方が安全。
    - >-
      「ハレーションゼロ」はモデル品質ではなく、locator、版、content hashがない引用を
      公開不能にするfail-closedなポリシーとして実装する必要がある。

Q2_design_coherence:
  decision: revise
  migration_feasible: true
  breaking_changes:
    - >-
      v2カードを5層ノードへ一対一変換してはいけない。既存K-IDは安定したハンドルとして残し、
      内容を原子claimへ分割し、各claimをノード版、scope、根拠、認識状態へ対応させる。
    - >-
      FableのL4は資料・ログ、AstraのL4は観測・操作可能な実体であり定義が衝突している。
      L4を実体・システム・プロセス・成果物に統一し、資料断片・観測・ログ・証明書は
      5層外のevidence storeへ移す必要がある。
    - >-
      nodes、node_revisions、claims、edges、evidence、support_assessments、
      approvals、eventsを分離する。既存33カードと101エッジは削除せずlegacy viewで公開する。
    - >-
      既存エッジは自動で新意味へ確定せず、決定的に変換可能、逆向き表示可能、要人手審査の
      3区分に分ける。特にuses、depends_on、isomorphic_toはclaim単位のscope監査が必要。
    - >-
      graph.pyはカード単位からclaim@revision単位へ拡張する。比喩遮断とemerges_from遮断は維持し、
      さらに承認範囲、依存失効、HYPからcanonicalへの根拠継承禁止を追加する。
    - >-
      P-K-Dは廃棄しない。Pは文脈・解釈・視点、Kはノード／claimハンドル、
      Dはevidenceまたはartifactへの互換ビューとして残せる。
    - >-
      append-only台帳はそのまま活用できるが、イベントに対象revision、claim_id、入力ハッシュ、
      ポリシー版、承認者を追加する。旧イベントは再書換えせず変換イベントを追記する。
    - >-
      ナッシュ均衡カードの形式的定義・存在定理と、人間行動を予測する経験的主張を分割する。
      同様に、Methodへ一律のfalsification_conditionを要求せず、claim kind別のwarrant profileを使う。

Q3_integration:
  a_evidence_store:
    decision: hybrid
    rationale: >-
      根拠ペイロードと根拠評価はAstra案どおり5層外に置く。
      evidenceはsource version、locator、content hash、origin groupを持ち、
      claimへの支持・反証は版付きsupport assessmentとして管理する。
      一方、論文ファイル、シミュレーター、測定装置、実験系そのものを対象として推論する場合は、
      それらをL4のArtifact/Systemとしても登録できる。この場合も、そのオブジェクト自体と
      そこから得た証拠を同一視しない。FableのSRC/LEC/LOGは主としてevidence kindへ移し、
      必要なものだけL4オブジェクトへの参照を併設する。

  b_node_granularity:
    decision: hybrid
    rationale: >-
      17型または12型という個数を物理スキーマの不変条件にしない。
      Astra型の少数の安定したノードクラスを採用し、FableのAXM/THM/DEF/THY/LAW/MTH等は
      claim kindまたは検証規則を持つfacetとして保持する。CAUやBNDも常に独立ノードにせず、
      再利用・版管理・個別反証が必要な場合だけ昇格させる。
      ただしHYPは独立したclaim lifecycleを持たせ、proposedからcanonicalへ直接遷移できない
      というFableの隔離規則を維持する。層ごとの別テーブルではなく、共通基盤と型別制約で実装する。

  c_edge_semantics:
    decision: hybrid
    rationale: >-
      Astraの「エッジの存在は根拠としての有効性を意味しない」を基本原則とし、
      Fableのformalized_byやinstantiatesが表す有用な区別を残す。
      ABSTRACTS_FROMを証明、経験的一般化、実装対応のすべてに使うことは禁止する。
      推奨分類は、DERIVES_FROM／FORMALIZED_BYを形式依存、
      HAS_SCOPED_INSTANCEを理論と局所モデルの対応、
      IMPLEMENTED_BYをモデルと実装の対応、
      GUIDES_TEST_DESIGN／CHECKSをワークフロー関係とする。
      evidencesは通常エッジから外し、evidenceとclaim間の版付きsupport assessmentにする。
      ABSTRACTS_FROMを使う場合はderivation_ref、scope変換、依存失効規則を必須にする。
      逆関係は表示時に生成し、instantiatesとHAS_SCOPED_INSTANCEのような逆エッジを二重保存しない。

  risk: >-

  mitigation: >-

    必要なderivation／evidence、禁止する継承を機械可読契約として定義する。
    第二価格オークションMVPで決定的実行、反例変異、根拠撤回、HYP隔離をテストし、
