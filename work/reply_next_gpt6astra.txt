## 提案：次は「需要起点・上限付きの草案補充パイプライン」を作る

質問生成や共活性化の高度化ではなく、既存の`query_gap_detected`を、次の一本の経路につなぎます。

```text
実際の質問
  → ローカル検索
  → 穴の候補を分類
  → 処理対象を選別
  → MIT OCWで候補発見
  → 原文取得・引用検証
  → 根拠付き草案を生成
  → 重複検査
  → concepts/_inbox/
  → 人間による確認
  → accepted
```

このフェーズの成果は、カード枚数ではなく、**「どの質問に応じ、どの原文から、いくら使って、この草案が作られたかを追跡できること」**です。

特に、現在の33枚がすべて未承認である点が重要です。**「acceptedに答えがない」と「新しい概念が必要」を分けないと、既存33枚の再生成が始まります。**

---

## 1. 最小のデータモデルとイベント種別

### ファイル構成

```text
concepts/
  _inbox/<card_id>.md
  accepted/<card_id>.md

sources/
  <source_id>.json          # URL、取得時刻、原文ハッシュ、必要な引用

.cache/
  ocw/<content_hash>        # 取得原文・抽出テキスト。Git対象外
  api/                     # 埋め込み・生成応答等。Git対象外

state/
  knowledge.sqlite3        # Git対象外

scripts/
  grow.py
  review.py
```

Gitにはカード、出典メタデータ、必要な引用、レビュー記録を残します。原質問、個人情報、APIキー、原文全文キャッシュはコミットしません。

### SQLiteの最小テーブル

既存のイベント・検索・共活性化テーブルは再利用し、以下を追加または拡張します。

| テーブル | 必須フィールド |
|---|---|
| `questions` | `id`, `text_local`, `text_hash`, `origin`, `domain`, `source_ref`, `root_id`, `parent_ids_json`, `generation_depth` |
| `gaps` | `id`, `question_id`, `gap_key`, `gap_type`, `requested_claim`, `existing_card_id`, `status`, `priority_reason` |
| `sources` | `id`, `url`, `final_url`, `fetched_at`, `content_hash`, `extractor_version`, `snapshot_path`, `source_family`, `quotes_json` |
| `cards` | `id`, `path`, `status`, `content_hash`, `root_id`, `parent_ids_json`, `generation_depth`, `source_ids_json`, `duplicate_status` |
| `jobs` | `id`, `kind`, `gap_id`, `idempotency_key`, `status`, `input_hash`, `result_ref`, `reserved_cost`, `actual_cost` |
| `budget_scopes` | `scope_type`, `scope_id`, `limits_json`, `reserved_json`, `spent_json` |

`budget_scopes`は`root_question`・`run`・`day`の三階層を持たせます。CLIを再実行しても、同じ質問の上限がリセットされないためです。

#### 質問の属性は二軸にする

```yaml
origin: real_user | synthetic | human_curated | unknown
domain: real_life | business | cross_science | definition | mechanism | ...
```

「実生活を題材にAIが生成した質問」は、

```yaml
origin: synthetic
domain: real_life
```

です。`domain`を実利用の証拠にしてはいけません。

`real_user`には実利用イベントへの`source_ref`を必須にします。人間が考えた探索問題も、実際に発生した質問でなければ`human_curated`です。

### 草案Markdownの最小形

```yaml
---
id: c_...
status: draft
root_question_id: q_...
generated_from: [q_...]
generation_depth: 1
source_ids: [src_...]
generator:
  model: ...
  prompt_version: ...
duplicate_status: pending
---
```

本文は最低限、次を分けます。

```markdown
# 概念名

## 対象とする問い
...

## 定義・機構
- 主張A ... [S1:Q1]

## 適用範囲・境界
...

## 根拠
- S1: 実際に取得したURL
- Q1: 原文に存在する引用

## 未確認事項
- 現実場面への適用は未検証
```

**定義・機構の根拠と、現実の問題に適用できるという仮説を混ぜない**ことが重要です。OCWの説明が、そのまま特定企業や生活場面での因果的有効性を証明するわけではありません。

### イベント種別

既存イベントに、以下を加えます。

```text
question_recorded
retrieval_completed
query_gap_detected          # 既存。意味は「穴の候補」
gap_triaged                 # 選択／保留／既存カード確認へ振り分け

ocw_search_completed
source_snapshot_recorded
source_validation_failed

draft_created
duplicate_check_completed

review_requested
card_approved
card_rejected
revision_requested

external_call_reserved
external_call_finished
job_stopped
```

共通フィールド：

```text
event_id, occurred_at, actor_type, run_id,
root_id, subject_id, parent_ids, generation_depth,
idempotency_key, payload
```

イベントは削除・訂正せず、後続イベントで状態を変更します。

既存ログがSQLiteなら、状態更新とイベント追記を同一トランザクションにします。ファイルログなら、SQLiteのoutboxを介して追記し、二重書き込みの不整合を避けます。

### 既存33枚の扱い

最初に台帳化します。

- `status=draft`
- 出典を未検証なら`provenance_status=unverified`
- 生成経路不明なら`generation_depth=unknown`
- 不明な出典ID・生成履歴は補作しない
- 深度不明のカードを自動生成連鎖の起点にしない
- 重複検査の対象には含める

## 2. 実行順序と、各段階の判定

### ① 実質問を登録する

入口は実利用ログ、または出所を確認できる実際の相談です。

- 原文はローカル保存
- 個人名・顧客名・社内数値等を外部送信用データから除外
- 正規化ハッシュで同一質問の再処理を抑制
- 同じ質問の再試行を新しい需要として数えない

### ② 質問生成は「必要時の具体化」に限定する

この段階で質問格子を全面的に回しません。

既存格子は、実質問の未回答部分を具体化するために使います。初期実装では、人間の選択またはテンプレートによる**最大1問の派生**に限定します。

```text
実質問                    depth=0
  └─ 派生質問             depth=1
       └─ 草案カード      depth=2 → 自動派生終了
```

直接草案化する場合：

```text
実質問                    depth=0
  └─ 草案カード           depth=1
```

生成物を材料に次を生成するとき、親の最大深度に1を加えます。

- 検索や原文取得は深度を増やさない
- 外部原文を取得しても、質問の生成履歴はリセットしない
- 人間承認でも生成深度をリセットしない
- 複数の親がある場合は最大深度を継承する

最初のCLIでは質問生成をデフォルトOFFにして構いません。**既存の穴を埋める方が先です。**

### ③ ローカル検索を二つのレーンで行う

```text
A. accepted検索：利用可能な確認済み知識
B. 全カード検索：_inboxを含む重複・未承認知識の確認
```

初期状態ではAが空でも、Bには33枚あります。

検索の実行順：

1. タイトル・別名の完全一致
2. BM25
3. キャッシュ済み質問埋め込みがあれば、既存ベクトル検索とRRF
4. 必要な場合のみ、未キャッシュ質問をまとめて埋め込み

埋め込みを使わなかった検索は、`retrieval_mode=bm25_only`と記録します。ハイブリッド検索を実行したことにはしません。

### ④ 穴を分類する

| `gap_type` | 意味 | 次の処理 |
|---|---|---|
| `unreviewed_only` | `_inbox`に答えの候補がある | 既存カードの根拠補完・レビューへ |
| `retrieval_failure` | 表記・索引・検索方法の問題らしい | 検索改善へ。新規生成しない |
| `source_missing` | 関連カードはあるが根拠不足 | 既存カードの出典補完へ |
| `coverage_candidate` | 全カードでも必要な説明が見つからない | OCW探索候補 |
| `out_of_scope` | OCW由来の概念補充では解決しにくい | 保留・別経路 |

BM25の低スコアだけでは`coverage_candidate`を確定しません。検索失敗は知識不存在の証明ではありません。

33枚規模の初期運用では、`grow plan`が上位候補と不足事項を表示し、**人間が短く分類確認してから外部検索する**方式を勧めます。

優先順位は、まず単純で十分です。

```text
確認済みの実質問
  > 人間が処理対象に選んだ探索質問
  > 自己生成だけの質問
```

自己生成だけの穴は、デフォルトでは外部探索予算を与えません。

### ⑤ MIT OCW検索で候補を発見する

一つの穴について：

1. ローカルで匿名化した検索語を作る
2. 設定済み検索手段でOCWを検索
3. 上位候補のURLを保存
4. 許可されたOCWドメインから原文を取得

実装はアダプターにします。

```python
discover_ocw(query, limit=3) -> list[SearchHit]
fetch_source(url) -> SourceSnapshot
```

利用可能な公式検索APIがあるとは仮定しません。採用する検索手段の仕様・利用条件・料金を確認して設定します。

重要な区別：

- 検索結果・スニペット：発見用
- 実際に取得した教材本文：草案の根拠候補

取得できなければ`no_source`で停止します。

### ⑥ 原文と引用を検証する

`source_id`は内部IDです。MITが発行したIDであるかのように扱いません。

保存項目：

```text
実取得URL・最終URL
取得日時
原文ハッシュ
抽出テキストのハッシュ・抽出器バージョン
引用の開始／終了位置
引用文字列
```

機械検証：

- 最終URLも許可ドメイン内か
- 取得・抽出が成功したか
- 引用が保存した抽出テキストの該当位置に一致するか
- 草案の出典参照が、今回取得した出典集合内にあるか

URLや引用をLLMに自由生成させません。出典集合はコード側で確定します。

なお、**引用文字列の一致は、主張を意味的に支えることの保証ではありません。** その確認は最終レビューに残します。

### ⑦ 安価なモデルで草案を生成する

Flash-LiteまたはHaikuに送るものを限定します。

```text
匿名化した対象質問
必要な説明項目
検証済み出典の関連箇所
出典ID・引用ID
固定JSONスキーマ
```

送らないもの：

- 全カード
- 実利用ログ全体
- 共活性化グラフ全体
- 顧客情報
- 不要な原文全文

出力はまずJSONにし、ローカル検証後にMarkdownへ変換します。

制約：

- 一つの穴から新規草案は最大1枚
- 根拠不足なら`insufficient_evidence`
- 支持されない説明を埋めない
- 新しい問いを出力しても、その場では実行しない
- AIによる自己採点を承認や独立証拠にしない

### ⑧ 重複を検出する

外部検索前の簡易検査に加え、生成後にも全カードと比較します。

1. 内容ハッシュ・正規化タイトル・別名
2. BM25による近傍候補
3. 利用可能なら保存済み埋め込み
4. 定義、対象、適用範囲の比較をレビュー画面に表示

結果：

```text
exact_duplicate    → 新規カード作成を抑止
possible_duplicate → 人間レビュー待ち
apparently_new     → 新規候補としてレビュー待ち
```

`apparently_new`は「新規性が証明された」ではありません。

類似カードとの自動マージ、既存acceptedカードの自動上書きはしません。初期版では、既存カードへの補完案件はキューに戻すだけでも十分です。

### ⑨ 人間承認ゲート

人間は最低限、次を確認します。

- 原文が実在し、引用と主張が対応する
- 適用範囲を広げすぎていない
- 既存カードと重複していない、または差分が明確
- 未確認事項が明示されている
- 対象質問との関係が妥当

承認イベントには、**確認したカードのハッシュと出典ハッシュ**を記録します。内容が変われば、その承認は流用できません。

自動ワーカーには`accepted`への書き込み権限と承認コマンドの実行権限を与えません。

## 3. 自己生成ログと実利用ログの分離

物理的に別DBにする必要はありません。共通イベントログに由来を必須化し、SQLiteのビューを分けます。

```text
real_usage_view
  実際の利用者の質問・その検索結果

synthetic_probe_view
  自己生成質問・自動派生質問・評価実行

curated_exploration_view
  人間が選んだ探索問題
```

由来不明の旧ログは`unknown`とし、実利用に昇格させません。

| シグナル | 候補化してよいもの | 証拠にしてはいけないもの |
|---|---|---|
| 実質問 | その質問に対する需要、補充優先度 | 回答の正しさ、需要全体の大きさ |
| 実質問の共活性化 | Compositionの検討候補 | 因果、創発、概念間関係の正しさ |
| 自己生成質問の共活性化 | 探索用Composition候補、検索テスト | 実需要、独立した関係の裏付け |
| 自己生成質問の検索失敗 | 穴の候補 | 知識が本当に存在しないこと |
| 取得したOCW原文 | 引用が支える主張の根拠候補 | 引用範囲を超える現実適用 |
| AI草案・AIレビュー | 作業物、検査所見 | 独立した根拠 |

追加で記録すべき検索情報：

```text
retriever_version
index_snapshot
retrieval_mode
filters
result_ids
ranks
対象カードの当時のstatus
```

これにより、共活性化が検索設定変更によって生じた可能性を追えます。

同じ原文の別URL、抜粋、そこから生成した複数カードは、独立証拠の数として加算しません。`source_family`と生成履歴でまとめます。

## 4. コスト・通信量の上限、キャッシュ、停止条件

### 初期設定例

金額は達成目標ではなく、処理を止めるための上限です。実際の料金表で事前見積もりし、足りなければ処理件数を減らします。

```yaml
run:
  max_selected_gaps: 5
  max_cost_usd: 0.10
  max_concurrency: 2

root_question:
  max_ocw_search_requests: 1
  max_search_hits: 3
  max_source_fetches: 2
  max_download_bytes: 4194304
  max_generation_attempts: 1
  max_new_drafts: 1
  max_automatic_retries: 0
  max_generation_depth: 2

daily:
  max_cost_usd: 1.00

generation:
  max_gaps_per_request: 2
  max_input_tokens: 12000
  max_output_tokens: 3000

query_embedding:
  enabled_by_default: false
```

初期版の質問具体化はテンプレートで行い、LLM生成枠は草案に使います。LLMによる質問生成を後から追加するなら、その呼び出しも同じ根予算に含めます。

### バッチング

- カード埋め込み：新規・変更カードだけをまとめて更新
- 質問埋め込み：必要と判断された未キャッシュ質問だけをまとめる
- 草案生成：最大2件程度を、`gap_id`ごとに入力・出力を分離して一括処理
- MIT検索：複数の穴を曖昧な一つの検索語に混ぜない

生成バッチでは、別の穴の出典を流用していないかローカル検証します。

### キャッシュキー

| 対象 | キー |
|---|---|
| ローカル検索 | 質問ハッシュ＋索引バージョン＋検索設定 |
| 質問埋め込み | 送信テキストハッシュ＋モデル＋次元＋task type |
| OCW検索 | 検索語＋検索手段＋フィルター＋期限 |
| 原文 | URL対応表＋内容ハッシュ |
| 草案生成 | 質問＋出典ハッシュ集合＋モデル＋プロンプト版＋スキーマ版 |

検索失敗も短期間キャッシュし、同じ穴を毎回検索しません。草案生成がキャッシュヒットしても、新しい独立した確認として記録しません。

### 呼び出す前に予算を予約する

```text
BEGIN IMMEDIATE
  根質問・実行・日次の残予算を確認
  最大課金額、リクエスト数、送信量を予約
  jobと予約イベントを記録
COMMIT

外部呼び出し
  → 実使用量で精算
```

料金不明なら有料呼び出しを停止します。タイムアウトで課金状況が不明なら、予約分を消費扱いとして自動再試行しません。

### 停止条件

以下のどれかで停止し、理由を記録します。

- 次の生成が深度3になる
- 根質問・実行・日次のいずれかの上限に達する
- 外部送信用の匿名化・送信許可が未確認
- 原文取得不能、引用不一致、出典不足
- 重複が確定
- 生成結果がスキーマ不正
- 通信・課金状態が不明
- 対象がOCW補充の範囲外

**停止を別モデルへの切替や再質問で迂回しない**ことを、コード上の共通ガードにします。

## 5. 最初に実装するCLIと受け入れ基準

### 実装順序

#### Phase A：台帳・由来・dry-run

最初の一手は、外部APIを呼ばない`plan`です。

```bash
python scripts/grow.py inventory

python scripts/grow.py ingest \
  --from-real-events \
  --since 2026-01-01

python scripts/grow.py plan \
  --origin real_user \
  --limit 5 \
  --offline \
  --out plan.json
```

`plan.json`には次を出します。

```text
対象質問
検索したカードとstatus
不足している説明
gap_type
既存カードへの振り分け
外部送信予定の匿名化検索語
呼び出し回数・料金の最大見積もり
停止条件
```

**受け入れ基準**

- 33枚すべてがdraftとして台帳化される
- acceptedが空でも、既存draftを無視して新規生成候補にしない
- synthetic・unknownを実需要として集計しない
- `--offline`では外部通信がゼロ
- 同じログの再取り込みで質問・穴が重複しない

#### Phase B：OCW発見・原文検証

```bash
python scripts/grow.py acquire \
  --plan plan.json \
  --max-cost-usd 0.10
```

**受け入れ基準**

- 検索結果だけでは`source_validated`にならない
- URL・教材ID・引用の欠損をLLMで補完しない
- 許可外へのリダイレクトを拒否する
- 原文・引用のハッシュを保存する
- 上限超過時は次の呼び出しを行わない
- 同一入力の再実行はキャッシュを使う
- 根拠取得不能ならカードを作らず停止する

#### Phase C：草案生成・重複検査

```bash
python scripts/grow.py draft \
  --plan plan.json \
  --model <configured-cheap-model>
```

**受け入れ基準**

- 一つの穴から最大1枚
- 作成先は`concepts/_inbox/`のみ
- 出典参照が許可された取得済み集合に限定される
- 引用が原文に一致しなければレビュー待ちへ進めない
- 重複候補を表示し、既存カードを上書きしない
- 深度超過はAPI呼び出し前に拒否する
- 再実行でカードと外部呼び出しを重複させない
- 異常終了後も、保存済み応答から処理を再開できる

生成応答はファイル化前に保存し、Markdownは一時ファイルから原子的に配置します。外部処理結果が不明なジョブは、勝手に再送しません。

#### Phase D：人間承認

```bash
python scripts/review.py show c_123

python scripts/review.py approve c_123 \
  --expected-sha256 <reviewed_hash> \
  --reviewer <human_id>
```

**受け入れ基準**

- 草案・原文引用・重複候補を並べて確認できる
- 確認後に内容が変わったカードは承認できない
- 自動ワーカーは承認できない
- 承認・却下・修正要求が追記イベントとして残る
- accepted移動とレビュー記録をGit差分で追跡できる

### 最初の統合テスト

少なくとも次のケースを固定fixtureにします。

| ケース | 期待結果 |
|---|---|
| 既存draftで答えられる実質問 | 新規生成せず、既存カード確認へ |
| 本当に不足し、原文を取得できる質問 | 根拠付きdraftが1枚 |
| 原文を取得できない質問 | 草案なし、理由付き停止 |
| 引用を捏造したモデル応答 | 検証失敗 |
| synthetic由来の検索失敗 | 実需要に計上されない |
| 既存カードの言い換え草案 | 重複確認待ち |
| 予算不足・深度2からの派生 | 呼び出し前に停止 |
| 同じジョブの再実行 | 課金・カードが増えない |

まずはこのテストを通すことを完了条件にし、生成枚数の目標は置きません。

---

## 6. この段階で絶対に作らないもの

1. **共活性化から自動でacceptedなCompositionを作る機能**  
   候補の記録までに限定します。

2. **自己生成質問数を需要指標にするランキング**  
   生成量で需要を水増しできてしまいます。

3. **AI草案を根拠として、別のAI草案を正当化する機構**  
   草案は探索材料にはなっても、独立証拠にはなりません。

4. **自動承認・自動マージ・acceptedの自動上書き**

5. **無制限な質問拡張、検索再試行、自己批評ループ**  
   「根拠不足だからもう一度」は、停止条件を破る理由にしません。

6. **毎質問のGemini埋め込み、全知識基盤のプロンプト送信**

7. **検索スニペットだけからの根拠付きカード生成**

8. **因果・創発・真理を表す自動スコア**  
   この段階で測れるのは、取得・引用検証・由来・レビュー状態です。

9. **大規模なグラフDB移行やエージェント群**  
   33枚規模ではMarkdown、SQLite、既存検索、明示的ジョブで足ります。

---

### 最終的な優先順位

```text
1. 33枚の台帳化とログ由来の分離
2. query_gap_detectedの分類＋offline plan
3. 予算予約・キャッシュ付きOCW取得
4. 引用検証付き草案生成
5. 重複検査と人間承認
6. その後に、少量の自己生成質問を接続
```

最初に作るべきものは、カードを大量生産するスクリプトではありません。**「作る必要がある穴だけを選び、出典が取れなければ止まり、作っても草案で止まる」スクリプト**です。
