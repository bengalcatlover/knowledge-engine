## blueprint:

**設計の中心は「カード」ではなく、根拠と適用範囲を持つ主張です。**  
5層は分類タグではなく、それぞれ異なる構造と検証責務を持ちます。

ここでの「宇宙」は天文学分野ではなく、**対象・相互作用・状態変化・境界条件をまとめた、範囲限定の世界モデル**と定義します。

### 1. 5層の定義・型・属性・エッジ

以下の必須属性は、後述する共通属性に追加します。

| 層 | 定義・責務 | ノード型 | 層固有の必須属性 | 許可する主な出辺 |
|---|---|---|---|---|
| **基礎科学** | 下位モデルから抽出した、形式・論理・測定・比較の再利用可能な原理。数学的定義と経験的法則を区別する | `FormalPrinciple`、`MeasurementPrinciple` | 形式表現、変数の意味、成立条件、導出または証明、適用限界 | `ABSTRACTS_FROM → 科学` |
| **科学** | 特定領域における説明・予測・識別の方法。何を説明でき、何が反証になるかを持つ | `Theory`、`ScopedLaw`、`Method` | 対象領域、主張、前提、予測または識別条件、反証条件 | `ABSTRACTS_FROM → 宇宙`、`HAS_SCOPED_INSTANCE → 宇宙`、`GUIDES_TEST_DESIGN → 問い` |
| **宇宙** | 複数の対象がどの境界条件で相互作用するかを表す、実行可能または検査可能な世界モデル | `WorldModel` | 境界、対象ロール、状態変数、相互作用、遷移規則、外生変数、未モデル化要因 | `ABSTRACTS_FROM → オブジェクト`、`CONSTRAINS → オブジェクト` |
| **オブジェクト** | 観測・操作・再同定できる具体的対象。人、組織、装置、ソフトウェア、実験系など | `Entity`、`System`、`Process`、`Artifact` | 同一性、版・時点、状態、観測インターフェース、操作インターフェース、所属する世界モデル | `ESTABLISHED_BY → 検証`、`RAISES → 問い` |
| **問い・行動・検証** | 世界モデルを使って問いを立て、操作し、結果を証拠として返す実行層 | `Question`、`Action`、`Verification` | 問い：判定対象・仮説・合否基準。行動：入力・手順・権限・停止条件。検証：観測・比較対象・判定・限界 | 問い：`ABOUT → 宇宙/オブジェクト`、`PLANS → 行動`。行動：`EXECUTES_ON → オブジェクト`、`PRODUCES → 検証`。検証：`ANSWERS → 問い`、`CHECKS → 対象ノードの特定版` |

全層で追加許可するのは次の2種類に限定します。

- `CONTRADICTS`：特定主張への反証・不整合。
- `SUPERSEDES`：同じ対象の旧版を置換。旧版は削除しない。

**エッジの存在と、根拠としての有効性は別です。**

- `ABSTRACTS_FROM`：根拠付き下位主張から上位主張を導出する。
- `HAS_SCOPED_INSTANCE`：その概念の具体化先を示すだけ。一般理論の正しさを証明しない。
- `GUIDES_TEST_DESIGN`：検証設計に利用するだけ。結果を支持しない。
- `CHECKS`：検査対象を指すだけ。検査結果が自動的に合格になるわけではない。

### 2. 共通データ契約

```yaml
node:
  id: string
  revision: integer
  layer: foundation | science | universe | object | practice
  type: enum
  title: string

  admission:
    kind: derived | imported_reference
    # 既存知識の取り込みと、新しい抽象化を区別

  scope:
    domain: string
    population_or_system: string
    conditions: []
    exclusions: []

  claims:
    - claim_id: string
      statement: string
      kind: definition | theorem | empirical | abstraction | application_hypothesis
      assumptions: []
      evidence_refs: []
      derivation_ref: null
      epistemic_status:
        # 以下のいずれか
        unverified | source_supported | formally_verified |
        empirically_supported | contradicted

  lifecycle:
    status: draft | ready | approved | blocked | stale | superseded
    approval_scope: null | reference_use | model_assertion | test_plan
    approval_record: null

  id: string
  type: enum

  to: node_id@revision#claim_id

```

#### 根拠は別ストアで管理する

MIT講義、一次論文、実務記録、実験ログ、証明ファイルは、5層とは別の**根拠ストア**に置きます。講義を中心ノードにはしません。

```yaml
evidence:
  evidence_id: string
  kind: source_excerpt | observation | execution_log | proof_certificate
  source_uri: string
  source_version: string
  locator: string             # ページ・節・時刻・ログ行など
  content_hash: string
  excerpt_or_artifact_ref: string
  supports_claim: string
  support_role: definition | premise | derivation | observation | counterexample
  origin_group: string        # 同一起源の証拠を独立証拠と数えない
  limitations: []
```

出典が付いていても、その出典が主張を含意しなければ支持とは認めません。LLMの要約・合意・再生成は独立した根拠になりません。

### 3. 承認時の不変条件

1. **すべての上位ノードに下位ノードへの追跡経路がある。**
2. 新規の承認済み上位主張は、原則として以下の根拠経路を持つ。

   ```text
   基礎科学
     └─ABSTRACTS_FROM→ 科学
         └─ABSTRACTS_FROM→ 宇宙
             └─ABSTRACTS_FROM→ オブジェクト
                 └─ESTABLISHED_BY→ 検証 → 根拠ストア
   ```

3. 経験的な抽象化は、根拠の適用範囲を無断で拡大しない。一般化には追加検証か、明示的な証明が必要。
4. 応用予測は `application_hypothesis` に分離する。検証計画を承認しても、予測が事実になることはない。
5. 根拠依存グラフは、**版単位で有向非巡回**にする。問いと検証の運用上の往復は許すが、自己支持は許さない。
6. 根拠が変更・撤回されたら、依存する主張を `stale` にし、回答への利用を止める。
7. 既存Kの `reference_use` 承認は、出典付き参照としての利用許可であり、今回のMVPによる理論全体の再検証ではない。

### 4. 最小の実装構成

```yaml
storage:
  relational:
    - nodes
    - node_revisions
    - claims
    - edges
    - evidence_refs
    - approvals
    - events
    - jobs
  artifact_store:
    - source_snapshots
    - code
    - datasets
    - execution_logs
    - proof_certificates

services:
  proposal_api: 提案・差分・検証結果の登録
  policy_engine: 型制約・権限・根拠経路・予算・状態遷移の検査
  sandbox_runner: 再現可能なコード実行
  query_api: 承認範囲と根拠経路を付けて回答

write_rule:
  - モデルにDBの直接更新権限を渡さない
  - 状態変更は署名付きイベント経由
  - 提案者と承認者を分離
  - 各ジョブは入力ハッシュを持ち、再実行を冪等化
```

グラフDBやベクトルDBはMVPの必須条件ではありません。

## mvp:

### 対象：有限な第二価格競売を、実行から上位原理まで追跡する

**目的**は「理想化した競売の性質」と「人間に適用したときの予測」を混同せず、1本の世界モデルを構築することです。

設定：

- 入札者2人、単一財。
- 評価額・入札額は `{0,1,2}`。
- 落札者は最高入札者、支払額は他者の入札額。
- 同額時の順位は事前固定。
- 私的価値、準線形効用、共謀・予算制約・外部性なし。
- 実際の人間への介入や金銭支出は行わない。

### ノード一覧：10ノード

根拠ファイルは別ストアのレコードであり、このノード数には含めません。

| ID | 層・型 | 内容 | MVPでの到達状態 |
|---|---|---|---|
| **B-0100** | 基礎科学 / `FormalPrinciple` | 有限選択集合における「基準選択からの最大改善量」による最適性判定 | 証明付きの局所的抽象として承認 |
| **S-0100** | 科学 / `ScopedLaw` | 指定した有限第二価格競売では、正直入札が弱支配戦略であり、正直入札プロファイルがナッシュ均衡になる | 指定モデル内で形式検証済み |
| **K-0003** | 科学 / `Theory` | 既存のナッシュ均衡 | 出典監査後、参照利用のみ承認 |
| **K-0010** | 科学 / `Theory` | 既存のインセンティブ両立性 | 出典監査後、参照利用のみ承認 |
| **K-0007** | 科学 / `Method` | 既存のRCT | 出典監査後、検証設計への参照利用のみ承認 |
| **U-0100** | 宇宙 / `WorldModel` | 入札者・価値・入札・配分・支払い・効用を持つ閉鎖競売モデル | モデル境界と遷移を承認 |
| **O-0100** | オブジェクト / `System` | 上記競売を実装した版固定シミュレーターと検査用インターフェース | 再実行可能、実装適合性を承認 |
| **Q-0100** | 実行層 / `Question` | Q1：理想モデルで正直申告から利益の出る逸脱はあるか。H1：誘発価値を使う人間実験でも、第二価格方式は第一価格方式より申告乖離を減らすか | Q1は回答済み。H1は未検証仮説のまま |
| **A-0100** | 実行層 / `Action` | 全許容入力の厳密列挙、逸脱利得検査、実装変異に対する検査感度確認 | サンドボックス内で実行済み |
| **V-0100** | 実行層 / `Verification` | 出典監査、実行ログ、反例探索結果、B-0100の証明検査、限界の記録 | 形式的結果のみ支持。人間への効果は `not_run` |

B-0100の形式表現は、小さく明確にします。

\[
C(f,a^*,D)=\max_{a\in D}\{f(a)-f(a^*)\}
\]

有限非空集合 \(D\) と \(a^*\in D\) に対し、

\[
C(f,a^*,D)=0
\quad\Longleftrightarrow\quad
a^*\in\operatorname{argmax}_{a\in D}f(a)
\]

これは競売結果から経験的に一般化するのではなく、**競売の検証構造から抽出し、最大値の定義から別途証明する**原理です。

### エッジ一覧

```text
B-0100  --ABSTRACTS_FROM-------> S-0100
S-0100  --ABSTRACTS_FROM-------> U-0100
U-0100  --ABSTRACTS_FROM-------> O-0100
O-0100  --ESTABLISHED_BY-------> V-0100

K-0003  --HAS_SCOPED_INSTANCE--> U-0100
K-0010  --HAS_SCOPED_INSTANCE--> U-0100
K-0007  --GUIDES_TEST_DESIGN---> Q-0100

O-0100  --RAISES--------------> Q-0100
Q-0100  --ABOUT---------------> U-0100
Q-0100  --PLANS---------------> A-0100
A-0100  --EXECUTES_ON---------> O-0100@実行対象版
A-0100  --PRODUCES------------> V-0100
V-0100  --ANSWERS-------------> Q-0100#Q1
V-0100  --CHECKS--------------> O-0100@実行対象版
```

表示上は論理IDを使っていますが、保存時は版と主張IDを固定します。

例：

```text
O-0100@1：実行前のコードと仕様
A-0100@1：O-0100@1を入力として実行
V-0100@1：ログと検証結果
O-0100@2：V-0100@1で確認できた性質を付加
U-0100@2：O-0100@2から構成
```

これにより「自分が生成した説明を、自分の根拠にする」循環を防ぎます。

### 実行順

| 順序 | 実行内容 | 担当・ゲート |
|---|---|---|
| 1 | 対象範囲、スキーマ、合否基準、予算、権限を固定 | Fableが設計、人間が初期承認 |
| 2 | K-0003/K-0010/K-0007の本文・前提・実際の出典箇所を監査 | Flashが収集、Haikuが照合 |
| 3 | U/O/Qのドラフトを作成。H1を未検証仮説として分離 | Flash |
| 4 | Oの仕様を固定し、実装とは別の検査器を用意 | Flashが実装案、Haikuが検査案 |
| 5 | Aを実行。全許容入力について効用・逸脱・同額処理を検査 | 決定的ランナー |
| 6 | Vを作成。入力・コード・出力ハッシュ、反例、限界を保存 | Flashが整形、Haikuが監査 |
| 7 | 検証済みOからU、UからS、SからBを提案。Bには独立した証明を付ける | Flashが提案、Haikuが検査 |
| 8 | 根拠到達性、範囲逸脱、仮説混入、根拠撤回時の失効を自動検査 | ポリシーエンジン |
| 9 | 差分と根拠パケットを一括最終判定 | Astra |
| 10 | 承認された範囲だけを公開 | ポリシーエンジン |

既存Kの内容と出典は提示されていないため、手順2の監査済み状態を先取りして設定してはいけません。

### 完了条件

以下をすべて満たしたときに完了です。

- **再現性**：第三者が保存済み入力とコードから、同じ判定を再現できる。
- **判別能力**：第二価格を自己入札額による支払いへ変更した変異実装について、検査器が有利な逸脱を検出できる。
- **説明可能性**：「なぜ正直入札が均衡なのか」に、前提・計算・出典へ戻れる形で回答できる。
- **境界管理**：「人間も正直に入札するか」には、形式検証からは結論できず、H1は未検証だと回答する。
- **失効の伝播**：根拠や仕様を変更すると、依存する承認が `stale` になり、旧結論が無条件に再利用されない。
- **予算遵守**：承認済み予算内で終わる。

人間実験の成功や、ノード・関係・講義の増加は完了条件にしません。

| 既存K | 配置 | MVPで使う部分 | 禁止する飛躍 |
|---|---|---|---|
| **K-0003：ナッシュ均衡** | 科学 / `Theory` | U-0100において、他者の戦略を固定した単独逸脱から利益が得られないという判定の参照元 | 均衡の存在から、一意性・効率性・実際の収束を主張しない |

```yaml

outcome: abs(bid - induced_value)
randomization_unit: 独立セッションまたは独立した参加者群
treatment: second_price
control: first_price
required_design_checks:
  - 同一参加者の学習・持ち越し
  - 参加者間干渉
  - クラスタ構造を反映した解析
  - 必要精度に基づく標本設計
  - 欠測・除外・停止規則の事前指定
execution_status: not_authorized_in_mvp
epistemic_status: unverified
```

既存Kは書き換えて局所実験の結論にしません。**既存理論の参照資産と、今回確認した局所主張S-0100を分離**します。

## agent_contract:

以下は各製品の能力を断定するものではなく、**その名称に割り当てる運用契約**です。利用可能性・構造化出力・必要な文脈長などは導入時に確認し、不適合なら停止します。

### 役割と状態変更権限

| エージェント | 厳密な役割 | 許可される変更要求 | 禁止事項 |
|---|---|---|---|
| **Fable 5** | 初期アーキテクチャ、スキーマ、ゲート、評価基準、予算設計。必要時の設計変更 | `DesignProposal` の登録。人間承認後に設計版を有効化 | 日常の出典収集、要約、ノード大量生成、各再帰での呼び出し、自分の設計の単独承認 |
| **GPT-6 Astra** | 新しい上位抽象・最終公開差分の最終判定 | `Approve / Reject / RequestRevision` の署名付き判定。対象は特定版・特定範囲 | 常時探索、実装ループ、根拠の代筆、判定中の本文修正、自分で修正した内容の即承認 |
| **Gemini Flash Lite** | 出典取得、抽出、正規化、既存ID照合、局所提案、コード案、差分パケット作成 | `draft` の作成・更新、証拠候補の追加、許可済みジョブの投入 | `approved` への変更、仮説の事実化、予算増額、スキーマ変更 |
| **Haiku** | 提案者から分離した出典照合、型・前提・範囲の監査、検査器案、実行結果の監査 | `AuditResult` の登録、`ready` または `blocked` への遷移要求 | 最終承認、根拠のない欠落補完、出典にない内容を「妥当そう」で補うこと |

**実際に状態を書き換えるのはポリシーエンジンだけ**です。

```yaml
transitions:
  draft -> ready:
    requires:
      - schema_valid
      - mandatory_fields_present
      - provenance_resolved
      - haiku_audit_passed
      - deterministic_checks_passed

  draft|ready -> blocked:
    trigger:
      - missing_evidence
      - scope_violation
      - failed_test
      - budget_or_permission_violation

  ready -> approved:
    requires:
      - astra_signed_decision
      - all_invariants_pass
      - human_approval_if_required

  approved -> stale:
    trigger:
      - dependency_changed
      - source_retracted
      - accepted_counterexample
    executor: policy_engine
```

Haikuの「合格」は科学的真理の保証ではありません。監査項目を通過したという記録に限定します。

### コスト制御

- Fable：初期設計と、明示承認された設計変更だけ。
- Astra：自動検査済みの最終判定パケットだけ。
- 定常処理：Flash、Haiku、決定的ランナー。
- 自動検査に落ちた候補を、Astraへの相談で通そうとしない。
- 安価なモデルが失敗しても、高価なモデルへ無断でフォールバックしない。
- 高価な呼び出しの費用を予約できない場合、候補は `ready` で停止し、公開しない。

## recursion_rules:

### 1. 開始条件

再帰は「関連概念がありそう」では開始しません。次をすべて必要とします。

```yaml
start_when:
  - 未解決の問い・矛盾・予測失敗のいずれかがある
  - 解決すると変わる判断または行動が明示されている
  - 起点となるノードと根拠が版固定されている
  - 探索範囲・必要な検証・合否基準がある
  - 想定コストが残予算内である
  - 同一入力・同一範囲の実行中ジョブがない
```

上位抽象化については追加条件があります。

- 下位の根拠経路が検査済みである。
- 共通構造を形式的に記述できる。
- どの下位主張を保存し、どの詳細を捨てるか説明できる。
- 抽象化による範囲拡大を、証明または新たな検証で扱える。

### 2. 再帰の一周

```text
承認済みの問い／反例
  → 必要な根拠を取得
  → 下位の観測・実行・検証
  → 宇宙モデルの更新案
  → 科学的主張の局所抽象案
  → 必要な場合だけ基礎原理の抽象案
  → 独立監査・自動検査
  → 最終承認
  → 新しい問い、または未検証の応用仮説
```

毎回5層全部を更新する必要はありません。**変更の影響が届く層まで**を対象にします。

上位モデルから提案した応用は、必ず新しい仮説として実行層へ戻します。上位モデルの承認を、その応用の承認へ継承してはいけません。

### 3. 停止条件

| 条件 | 停止時の扱い |
|---|---|
| 問いの合否基準を満たした | 結果と限界を固定して終了 |
| 必要な一次資料・測定・権限が得られない | `blocked`。不足を明記 |
| 新しい根拠も、不確実性を減らす検査も得られない | `no_progress` として停止 |
| 既存主張の言い換え・循環支持しか生まれない | 重複として閉じる |
| 前提矛盾・反例・仕様不整合が出た | 関連主張を保留し、修正または人間へ |
| 予算・期限・安全制約に達した | 未完了状態を保存し停止 |
| 事前設定した再帰深度に達した | 人間の再承認まで停止 |

再帰深度やジョブ上限は暴走防止の制約であり、成功指標ではありません。

### 4. 承認条件

```yaml
approval:
  automated_gate:
    - 下位から根拠まで到達できる
    - 根拠依存に循環がない
    - 出典の内容と主張が対応する
    - 経験的範囲を無断拡大していない
    - 同一起源の根拠を重複評価していない
    - 応用仮説が事実と分離されている
    - 必要な再現検査が通る

  final_model_gate:
    authority: GPT-6 Astra
    required_for:
      - 新しい上位抽象
      - 公開する主張の意味変更
      - 矛盾解消後の再承認
    decision_scope:
      - 特定ノード版
      - 特定主張
      - 特定適用範囲

  human_gate:
    required_for:
      - 初期設計と予算
      - スキーマまたは権限変更
      - 予算増額
      - 人間への実験・外部送信・金銭支出
      - 不可逆な操作
      - 高影響な実務判断への展開
```

### 5. 成功指標

測るのは蓄積量ではなく、次の能力です。

- 問いに対し、**回答可能・未検証・前提外**を正しく分けられるか。
- 採用した結論を、出典・計算・観測まで再現できるか。
- 反例や根拠撤回によって、結論を適切に修正できるか。
- より少ない費用で、重要な判断の不確実性を減らせるか。
- 上位抽象が下位の既知結果を保存し、新しい適用では検証すべき差分を示せるか。

このMVPで成立させるのは、百科事典ではなく、**「根拠から抽象化し、応用を仮説として下ろし、検証結果で世界モデルを修正する」一周の閉ループ**です。
