# 設計レビュー回答

## 1. node_attribution精度向上の最適修正

**根本原因の推定**: ストップワード除去なしのJaccardでは "increase", "expected", "probability", "model" 等の汎用語が支配し、キーワード集合が広いノード（K-0007のような方法論ノード）がアトラクタ化する。閾値0.20は汎用語一致だけで容易に超える。

**選択肢比較**:

| 手法 | 精度 | コスト | 新ドメイン対応 |
|---|---|---|---|
| キーワード改善（stopword + IDF重み） | 中 | ほぼゼロ | △（語彙外は依然弱い） |
| ローカルembedding（multilingual-e5等） | 高 | 初期実装のみ、推論無料 | ○（意味類似で棄却判定可能） |
| LLM全件再分類 | 高 | claim数×候補提示で継続コスト | ○ |

**推奨: 段階的ハイブリッド**
1. 即時: stopword除去 + IDF重み付け（K-0007問題の大半はこれで消える）
2. 本命: embedding類似度で top-k候補 + **明示的な棄却閾値**（ランダムペアの類似度分布から較正）
3. 曖昧帯（棄却閾値±εのみ）Haikuで「候補リスト + NO_MATCH選択肢」の分類。全件LLMは不要、境界例のみでコスト最小化

## 2. K-0007の64件の扱い

**再帰属のみ（抽出結果は保持）**を推奨。

- 根拠: 誤っているのは**帰属**であり**抽出**ではない（claim文自体は妥当に見える）。削除→再抽出はLLMコストの純粋な無駄
- 手順: 64件の帰属リンクをdetach → 修正後パイプラインで再帰属 → unresolvedはnode_factoryへ
- 検証: 再帰属結果から10〜15件サンプリングして手動レビュー（全件手動は100ノード成長過程でスケールしない）

## 3. 鶏と卵問題への対処

**パイプラインに「棄却→クラスタリング→ノード提案」の経路を追加**:

```
evidence_miner → attribution（棄却可能）→ unresolved pool
  → embedding clustering → node_factory がクラスタ単位で新ノード候補生成
  → 再帰属で検証
```

- 新ドメイン投入時は「unresolvedが多いのが正常」。unresolved=0はむしろ異常シグナルとして扱う
- 補助策: 投入時にドメインタグを付与し、既存ノードのドメインと不一致なら帰属閾値を引き上げる（統計学ノードにオークション理論claimが吸われるのを構造的に防ぐ）
- 新ノードは初期HYP扱い→claim帰属が閾値超えでevidence-backed昇格、とすれば原則も維持できる

## 4. 致命的な設計問題

**ある。2点が致命的**:

1. **閉世界仮定（棄却クラスの欠如）**: 現行設計は「必ずどこかのノードに帰属する」前提。知識ベースが19→100へ成長する = 未知が多数派のフェーズで、abstention（該当なし）を持たない分類器は構造的に誤帰属を量産する。confidence<0.30の暫定修正は対症療法で、Jaccardスコアは較正された確信度ではない
2. **異常検知の欠如**: 1ノードに64件集中は明白な分布異常。「1バッチで1ノードへの帰属がN件超過なら警報」程度の監視すら無かった。ハブノード化は今後も別ノードで再発しうるため、帰属分布の歪度モニタリングを必須化すべき

副次的問題: バイリンガルマップ展開がトークン集合を膨張させJaccard分母/分子を歪めている可能性も確認を推奨。

**優先順位**: 棄却経路の導入(4-1) > stopword+IDF(1) > 再帰属(2) > クラスタリング経路(3)。
