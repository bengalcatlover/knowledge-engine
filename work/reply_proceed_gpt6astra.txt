# 結論：検索を直してから、知識表現を高度化する

実装順は次です。

1. **検索Recallを回復する**
2. **カードをバージョン付き・由来付きデータへ移行する**
3. **文脈付き検索・引用付き回答を完成させる**
4. **安全な自動増殖と共活性化マイニングを入れる**
5. **型付き不確実性と実行可能モデルを追加する**
6. **CompositionCardと創発Claimを再実行可能にする**
7. **認証・監視・バックアップを加えて製品化する**

最初からRDF、確率推論、シミュレータへ進むべきではありません。現在のボトルネックは明確に検索です。Recall@6が6%の状態では、その上にどれだけ高度な知識表現を作ってもユーザーから見えません。

```text

  perspectives/

  schemas/               # JSON Schema / Pydantic

```

役割を次のように分離します。

- **YAML/Markdown + Git**：人間が編集するCanonical Knowledge
- **SQLite**：検索投影、Assertion、イベント、由来、クエリログ
- **ベクトルファイル**：意味検索
- **Artifacts**：シミュレーション・軌道・実行結果
- **Snapshot manifest**：どのカード・索引・モデルで回答したか

現段階では、グラフDBや完全なイベントソーシングは不要です。

# Phase 1：検索Recallを救済する

## 目的

**今のシステムを最小限変えて、言い換え・シナリオ・日英横断検索を動かす。**

カードスキーマはまだ変えません。変更対象は検索パイプラインだけです。

## 何が動くようになるか

- ANDに一致しない言い換えでも候補が出る
- 日本語の質問から英語のMIT OCW講義を検索できる
- シナリオ問題から関連概念を経由して講義へ到達できる
- すべての検索結果にretriever versionを記録できる

## 実装順

### 1. AND検索を「複数経路検索」に変更する

一つの検索式にすべてを詰め込まず、以下を別々に実行します。

1. 完全フレーズ検索
2. OR-BM25検索
3. 英訳・同義語展開後のBM25検索
4. ベクトル検索
5. Concept → Lectureリンクによるブースト

各検索結果は生スコアではなく、RRFで統合します。

```python
def reciprocal_rank_fusion(result_sets, k=60):
    scores = {}

    # result_sets = [(weight, [doc_id, ...]), ...]
    for weight, ranked_ids in result_sets:
        for rank, doc_id in enumerate(ranked_ids, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + \
                             weight / (k + rank)

    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

BM25の生スコアは、クエリ変形ごとに分布が違うため直接足し合わせない方が安全です。

### 2. FTSをフィールド別に重み付けする

```sql
CREATE VIRTUAL TABLE documents_fts USING fts5(
    title,
    aliases,
    summary,
    mechanism,
    body,
    doc_id UNINDEXED,
    doc_kind UNINDEXED,
    tokenize = 'unicode61 remove_diacritics 2'
);
```

検索例：

```sql
SELECT
    doc_id,
    doc_kind,
    bm25(documents_fts, 10.0, 8.0, 4.0, 2.0, 1.0) AS score
FROM documents_fts
WHERE documents_fts MATCH ?
ORDER BY score
LIMIT 50;
```

FTS5の`bm25()`は小さい値ほど上位です。

安全なORクエリ生成：

```python
import re

def fts_escape(term: str) -> str:
    term = re.sub(r'["*:^()]', ' ', term)
    term = re.sub(r'\s+', ' ', term).strip()
    return f'"{term}"'

def make_or_query(terms: list[str]) -> str:
    terms = [t for t in terms if len(t.strip()) >= 2]
    return " OR ".join(fts_escape(t) for t in terms)
```

### 3. 日本語対策を入れる

`unicode61`だけでは日本語の分かち書きが弱いため、次のどちらかを使います。

- 最小実装：日本語質問を英語へ翻訳してMIT OCW検索
- 改善実装：SudachiPyで日本語を分かち書きしてから格納・検索

4,258講義程度なら、以下の構成で十分です。

- 日本語カード：Sudachiで分かち書き
- MIT OCW：英語の原文
- 質問：日本語原文、分かち書き、英訳の3種類を生成
- ベクトル：多言語埋め込みを1種類

### 4. ベクトル検索を追加する

4,258講義＋カード数百程度なら、まだ専用ベクトルDBは不要です。

- 埋め込みをNumPy/FAISS/sqlite-vecのいずれかに保存
- `title + course title + summary + keywords`を埋め込む
- モデル名・バージョン・生成日を必ず記録

```python
def build_embedding_text(doc):
    return "\n".join([
        f"title: {doc.title}",
        f"aliases: {'; '.join(doc.aliases)}",
        f"summary: {doc.summary}",
        f"concepts: {'; '.join(doc.related_concepts)}",
    ])
```

### 5. 上位30〜50件のみrerankする

検索全件をLLMへ渡さず、RRF上位30〜50件だけをrerankします。

最終フロー：

```text
質問
  ├─ 原文OR-BM25
  ├─ キーワード展開BM25
  ├─ 英訳BM25
  ├─ 多言語ベクトル検索
  └─ Concept/Lectureリンク展開
          ↓
         RRF
          ↓
      上位30〜50件
          ↓
      reranker
          ↓
        上位6件
```

## 評価基準

元の50問は変更せず回帰テストとして固定します。ただし50問だけでは小さすぎるため、フェーズ3までに200問へ増やします。

フェーズ1の終了条件：

- Recall@6：**6% → 最低45%**
- Recall@20：**70%以上**
- シナリオ問題サブセット：Recall@6 **35%以上**
- 検索結果0件率：**5%未満**
- p95レイテンシ：reranker込みで**3秒以内**
- 各結果に検索経路とスコア内訳が残る

45%に到達しなければ、次の知識基盤改修へ進まずエラー分類を続けます。

## 工数

8〜12人日。

# Phase 2：バージョン付き知識基盤へ移行する

## 目的

カード、主張、由来、候補、スナップショットを分離する。

完全なRDF化ではなく、既存カードを壊さずに包む形で移行します。

## 何が動くようになるか

- 「どのバージョンの知識で回答したか」を再現できる
- CandidateとAcceptedを検索時に明確に分離できる
- 主張ごとにTruthValue、由来、文脈を持てる
- 自動生成物が独立証拠として自己増殖するのを防げる
- カード変更をロールバックできる

# Phase 3：文脈付き検索と引用付き回答

## 目的

`core + delta + Facet/Lens`を実際の回答パイプラインへ接続する。

## 何が動くようになるか

- 科学・工学・ビジネス・日常の意味差を分離できる
- 比喩を科学的事実として混入させない
- 回答中の主張をカード・講義・外部証拠まで追跡できる
- `as_of`を指定して過去の知識状態で再実行できる
- この段階で限定用途の有償パイロットが可能になる

## 文脈は最初から細分化しない

初期Contextは以下だけで十分です。

```yaml
Context:
  domain: science | engineering | business | everyday
  task: learn | explain | decide | troubleshoot
  audience: beginner | practitioner | expert
  locale: ja-JP | en-US
```

## Facet解決

```python
def resolve_facet(card, context):
    candidates = []

    for facet in card.get("facets", {}).values():
        condition = facet.get("applies_when", {})
        matched = sum(
            context.get(k) == v for k, v in condition.items()
        )
        if matched == len(condition):
            candidates.append((matched, facet))

    candidates.sort(key=lambda x: x[0], reverse=True)

    if len(candidates) >= 2 and candidates[0][0] == candidates[1][0]:
        return {
            "kind": "ambiguous",
            "candidates": [candidates[0][1], candidates[1][1]]
        }

    return candidates[0][1] if candidates else card["core"]
```

同順位の場合、暗黙に一方を選ばず`Ambiguous`を返します。

# Phase 4：統制された自動増殖と共活性化

## 目的

現在の `_inbox/` 自動生成を、安全な成長パイプラインへ変える。

## 何が動くようになるか

- 不足概念を回答後に非同期生成できる
- 重複カードや自己引用を検出できる
- 人間が差分を見て昇格できる
- 共活性化から「概念の穴」やCompositionCard候補を発見できる
- 使用頻度と真理性を分離できる

## クエリと更新を同じトランザクションにしない

```python
def answer_query(request):
    snapshot = acquire_snapshot(request.as_of)
    result = execute_query(request, snapshot)

    append_event({
        "type": "QueryServed",
        "snapshot_id": snapshot.id,
        "query_id": request.id,
        "result_ids": result.ids
    })

    enqueue_gap_analysis(request.id)  # 非同期
    return result
```

## Candidate生成条件

すべての質問からカードを作らないでください。例えば次を満たした場合だけ候補化します。

```text
以下のいずれか:
- top retrieval scoreが閾値未満
- 回答に引用できない重要概念がある
- 同一概念クラスタが3つ以上の独立セッションで出現
- ユーザーが「概念化して」と指定

かつ:
- 既存カードとの類似度が0.90未満
- 少なくとも1つ外部証拠がある
- 生成連鎖深度が2以下
```

- 既存CompositionCardがない集合

## 重要なルール

- 検索回数は証拠ではない
- AI生成カードは、そのカード自身の独立証拠にならない
- 同じ元資料を引用する複数生成物は1証拠群として数える
- 人気度はランキングに最大10〜15%だけ寄与させる
- 人気度には時間減衰を入れる
- Acceptedへの更新は必ず次Snapshotから反映する

# Phase 5：TruthValueと実行可能モデル

## 目的

連続性・確率・不確実性を、説明文ではなく実行可能なインターフェースとして扱う。

## 何が動くようになるか

- 「増加中」「定常状態」「閾値超過」などを定性的に推論できる
- 数値入力が揃えば外部モデルを実行できる
- Probability、Fuzzy、Interval、Unknownを区別して返せる
- 実行結果をArtifactとして保存し、再実行できる

## 最初に対応するTruthValue

以下だけで十分です。

```text
Boolean
Probability
FuzzyMembership
Interval
Unknown
```

Belief Mass、四値論理、全体ベイズネットは後回しです。

## モデル定義例

```yaml
id: model:logistic-growth
version: 1
kind: continuous_dynamic_model

entrypoint: models/logistic.py:run
code_hash: sha256:...

inputs:
  N0: {type: number, unit: count}
  r:  {type: number, unit: 1/day}
  K:  {type: number, unit: count}
  days: {type: integer, unit: day}

outputs:
  trajectory:
    type: timeseries
    unit: count

qualitative_regimes:
  - id: early_growth
    condition: "N < 0.2 * K"
    trend: increasing_accelerating

  - id: saturation
    condition: "N >= 0.9 * K"
    trend: increasing_decelerating

validity_conditions:
  - "K changes slower than N"
  - "population is approximately homogeneous"

resource_policy:
  timeout_seconds: 10
  network_access: false
  max_memory_mb: 256
```

カード側はモデルを参照します。

```yaml
id: concept:logistic-growth

  - model_ref: model:logistic-growth
    applicability:
      - "resource limitation exists"
      - "carrying capacity can be approximated"
```

## 実行結果はカードへ書き戻さない

```yaml
artifact_id: trajectory:abc123
model_ref: model:logistic-growth
model_version: 1
snapshot_id: snap_a94f

inputs:
  N0: 300
  r: 0.12
  K: 10000
  days: 365

storage_ref: artifacts/trajectories/abc123.parquet
execution:
  code_hash: sha256:...
  started_at: ...
  duration_ms: 42
```

カードに「365日後は9,999」と保存すると、入力条件が失われて知識と実行結果が混ざります。

## セキュリティ

- AI生成コードを直接実行しない
- 許可済みentrypointだけをregistryへ登録
- コンテナまたは制限付きsubprocess
- ネットワーク遮断
- CPU、メモリ、時間制限
- 入出力JSON Schema検証
- コードhash記録

## 最初に実装するモデル

3〜5個で十分です。

- 指数成長
- ロジスティック成長
- ベイズ更新
- 待ち行列
- 単純なフィードバック／在庫振動

全カードへモデルを付ける必要はありません。

## 工数

15〜25人日。

# Phase 6：CompositionCardと創発Claim

## 目的

創発を「説明文」ではなく「再実行可能な観測済みClaim」にする。

## 何が動くようになるか

- 構成要素、相互作用、更新方式を明示できる
- パラメータ掃引・複数Seedで実験できる
- マクロ観測量を検出できる
- `emerges_from`を`has_part`と分離できる
- 創発結果を再現可能な研究Artifactとして残せる

## CompositionCard例

```yaml
id: composition:flocking-v1

  - cohesion

  dimensions: 2
  boundary: periodic

```

# 3. 依存関係

```text
Phase 1: Hybrid Retrieval
   ├──────────────→ Phase 4: 共活性化ログ
   │                    │
   │                    └──────────────┐
   ↓                                   ↓
Phase 2: Revision / Assertion /       Phase 6: Composition /
         Evidence / Snapshot           EmergenceClaim
   ├──────────────→ Phase 3: Context       ↑
   │                    │                  │
   │                    └→ Phase 4 ───────┘
   │
   └──────────────→ Phase 5: TruthValue /
                         Model Runtime ────┘

Phase 3 ───────────→ Phase 7: 製品運用
```

重要な依存関係は以下です。

- **共活性化マイニングはPhase 1のログに依存**
- **自動昇格はPhase 2のRevision・Evidence・Snapshotに依存**
- **FacetはPhase 2のAssertion/Context表現に依存**
- **創発ClaimはPhase 4のComposition候補とPhase 5の実行基盤に依存**
- **有償運用は最低でもPhase 3の引用・監査可能性に依存**

# 4. 「ここまで来たら売れる」

## 有償パイロット：Phase 3完了時点

ただし「世界のあらゆる知識基盤」としてではなく、用途を限定して売ります。

売り方の例：

- MIT OCW横断学習アシスタント
- 経済学・CS・統計を横断する概念ナビゲータ
- 企業内ナレッジの引用付き検索・回答
- 属人知から科学概念への逆引き支援

必要条件：

- Recall@6が少なくとも50〜60%
- 引用率95%以上
- 回答のSnapshot再現
- CandidateとAcceptedの明示
- 1つの狭い領域で150〜300枚程度の検証済みカード
- 顧客の代表質問100〜200件による受入評価

現在の33枚だけで「汎用知識基盤」を販売するのは難しいです。Phase 3時点では**広さではなく、監査可能性と概念横断性**を売るべきです。

## 差別化された製品：Phase 4完了時点

ここで初めて、

> 利用されながら不足概念を発見し、人間の統治下で成長する知識基盤

という独自性を商品説明に使えます。

## エンタープライズ販売：Phase 7完了時点

認証、監査、データ分離、バックアップが揃ってからです。

# 6. やらなくてよいこと

少なくとも現時点では、以下は過剰設計です。

## データ基盤

- RDF-starへの全面移行
- Neo4jなどのグラフDB導入
- すべてをイベントから再構築する完全Event Sourcing
- 数十枚のカードに対する分散DB
- 専用ベクトルDB

SQLite、Git、ファイルArtifactで十分です。

## 確率・論理

- 全カードを結ぶ大域ベイジアンネット
- Dempster–Shafer、Belnap四値論理の全面実装
- 確率・検索スコア・証拠品質の統一
- 厳密な確率キャリブレーションを全カードへ要求

最初はBoolean、Probability、Fuzzy、Interval、Unknownだけにします。

## 連続モデル

- PDE一般ソルバ
- Modelica/FMU全面統合
- 自動数式発見
- 全カードへの実行モデル付与
- AIが生成した任意コードの直接実行

需要の高い3〜5モデルから始めます。

## 文脈

- 完全な文脈論理
- 無制限のマイクロセオリー
- 地域・職種・年代ごとのFacetを事前生成
- FacetをOOP継承ツリーにすること

「実際に意味衝突が起きたときだけFacetを追加」が正解です。

## 創発

- 未知の創発現象の自動予測
- マクロ観測量の完全自動発見
- ε-machineやトポロジカルデータ解析の早期導入
- 共起しただけで`emerges_from`を付けること

共活性化はComposition候補であり、創発の証拠ではありません。

## 自動成長

- 自動生成カードの即時Accepted化
- 利用回数を真理の証拠として使うこと
- 自己生成物を独立証拠として数えること
- 同一Snapshot内で検索結果を学習・反映すること
- 複数AIエージェントによる無制限な自己増殖

# 最終判断

最短で価値を出すクリティカルパスは次です。

```text
検索修復
 → 回答の引用・再現性
 → 文脈分離
 → 統制された自動成長
```

TruthValue、連続モデル、創発シミュレータは重要ですが、製品価値の最短経路ではありません。先に検索と統治を完成させるべきです。

実務上の最初の成功状態は、

> 質問すると関連概念とMIT講義が高い確率で見つかり、どの知識バージョン・文脈・証拠に基づく回答か追跡でき、不足概念は勝手に本番採用されずレビュー待ちになる

という状態です。これはPhase 3、約7〜9週間で到達可能です。
