## Definition
状態機械とは、**システムが離散的で有限の「状態」の集合の中に常に存在し、イベントや条件に応じて状態から状態へ遷移する枠組み**である。交差点の信号機（赤→青→黄→赤）、自動販売機（待機→商品選択→決済完了）、または会社の請求プロセス（未送信→送信済→支払済→完了）など、段階的に進む任意のプロセスを形式化できる。各状態では特定の動作が許可され、そうでない動作は拒否される。

## Mechanism
状態機械の構造：

```
状態集合 Q = {q0, q1, q2, ...}
入力アルファベット Σ = {事象1, 事象2, ...}
遷移関数 δ: Q × Σ → Q
  例： δ(赤, タイマー満了) → 青

現在状態 q_current と入力 a に対して：
  q_next = δ(q_current, a)
```

**自然言語での実行メカニズム**：
1. システムがある状態（例：「支払待ち」）にいる
2. 外部イベント（例：「クレジットカード承認」）が発生
3. 遷移関数がこの (状態, イベント) の組を見て「次の状態は『完了』」と決定
4. システムは新しい状態に移行し、その状態での動作ルールが発動

状態ごとに異なるルールセットが存在することが本質：状態Aでは禁止されている操作が、状態Bでは許可される。

## Boundary Conditions
状態機械がモデリング能力を失う（壊れる）条件：

1. **状態数が爆発的に増える**：N個の独立した変数があると、状態数は2^N になる（状態爆発問題）。例えば、ユーザーの「ログイン/ログアウト」「プレミアム/通常」「アクティブ/非アクティブ」という3つの二値変数で8状態必要
2. **連続的な値や無限精度が必要**：温度制御で「温度は15.3456...°C」というように無限に微妙な値を状態として記録する必要がある場合、有限状態機械では不十分
3. **並列プロセスの相互作用**：複数のエージェントが独立に動く場合、状態の組み合わせが指数関数的に増える
4. **確率的な挙動が本質的**：「50%の確率で状態Aへ」という非決定論的遷移は基本的な有限状態機械では扱えない（確率的オートマトンが必要）
5. **無限の未来を考慮する必要がある場合**：「いつかは終了する」と保証できないシステム

## Failure Modes
不適切に状態機械を使った場合の観察可能な問題：

- **状態爆発による複雑さ**：保守不可能なほど多くの遷移ルールが必要になり、バグが増殖
- **デッドロック**：ある状態から脱出する遷移が存在しない（例：「キャンセル不可」なまま）
- **未定義の遷移**：予期したイベントに対する遷移ルールが存在せず、エラーになる
- **過度な単純化**：実際には「保留中」という曖昧な状態があるのに、「完了」と「未完了」の2状態しかモデル化しない

## Business Transfer

### シナリオ1：注文フルフィルメントパイプライン
**適用**：電商プラットフォームで注文ステータスを状態機械でモデル化：
- 状態：{未確認 → 支払確認 → ピック → パック → 発送 → 配達完了 → 返却可能 → 返却不可}
- イベント：支払完了、在庫確認、配達完了など
- 各状態でのルール：例えば「配達完了状態でのみ返却を受け付ける」
**Caveat**：複数商品の注文で各SKUが異なる状態遷移をしている場合、注文全体の状態を定義するのが複雑化する。「部分配達」という状態を追加するかどうかで状態数が大きく増える。

### シナリオ2：SaaS請求サイクル管理
**適用**：サブスクリプション企業で顧客アカウントのステータスを管理：
- 状態：{トライアル → アクティブ → キャンセル予定 → サスペンド → キャンセル完了}
- 遷移トリガー：カード有効期限切れ→サスペンド、キャンセル申請→キャンセル予定、など
**Caveat**：「一時停止中に再開」という操作が許可される場合、状態定義が曖昧になりやすい。また、同じ「サスペンド」状態でも理由（支払い失敗 vs 管理者による停止）が異なると、許可される操作が変わる可能性があり、隠れた状態が必要になる。

### シナリオ3：ワークフロー承認フロー
**適用**：経費精算ワークフローで申請の進行状況を追跡：
- 状態：{草稿 → 提出 → 一次承認待ち → 二次承認待ち → 却下（→草稿に戻る）→ 承認完了 → 支払い完了}
- イベント：「却下」で以前の状態に戻る（遷移の非単調性）
**Caveat**：複数の承認者が並列に同じドキュメントを承認する場合、「2人とも一次承認待ち中」という状態を正確にモデル化する必要がある。状態機械では基本的に単一の状態しか持てないため、こうした並列プロセスは一度に複数状態の組み合わせが必要になり、爆発的に複雑化する。

## Non-Examples

- **制御フロー（if-then-else）**：プログラムの条件分岐。状態が保持されず、毎回フレッシュに判定される
- **データベースのERモデル**：「ユーザーテーブル」のように多数の属性を持つもの。状態の列挙的な離散化ではなく、属性の組み合わせ
- **確率的プロセス**：遷移が決定論的ではなく、分布に従う（例：マルコフ連鎖では遷移確率が存在）
- **スケジューラ**：「9時に実行、10時に実行」といった時間ベースの制御。状態遷移ではなくタイムトリガー
